# 第十章：实施与运维部署上线手册

> 适用对象：实施顾问、运维工程师、交付经理  
> 使用目标：把 JVS-APS 从本地样例跑通，推进到试点部署、上线切换和稳定运行

---

## 1. 手册范围

这份文档重点解决：

1. 环境怎么准备。
2. 数据库和应用怎么部署。
3. 上线前要检查什么。
4. 运行中要监控什么。
5. 当前版本有哪些必须提前告知客户的边界。

---

## 2. 当前项目的交付定位

基于当前代码，JVS-APS 的交付定位应定义为：

1. 可以做本地演示和功能验收。
2. 可以做单工厂、单租户试点。
3. 已具备业务闭环，但平台治理尚未完全企业化。

上线前必须提前说明的现实边界：

1. 租户被固定为 `1`。
2. 没有完整鉴权与权限体系。
3. 配置文件未按环境拆分。
4. 求解器仍和管理服务同进程。
5. 高级策略参数后端已支持，但前端未完整开放。

## 3. 环境要求

### 3.1 软件版本

| 组件 | 版本要求 |
|------|---------|
| JDK | 17 |
| Maven | 3.8+ |
| Node.js | 16.14+ |
| npm | 8+ |
| MySQL | 8.0.x |
| Redis | 6.x |
| Docker | 推荐 |
| Docker Compose | 推荐 |

### 3.2 服务器建议

试点环境建议：

1. CPU：4 核起。
2. 内存：8GB 起。
3. 磁盘：50GB 起。

如果订单量、资源量较大，建议提高：

1. CPU 到 8 核以上。
2. 内存到 16GB 以上。

### 3.3 时区要求

后端、数据库、应用服务器建议统一：

```text
Asia/Shanghai
```

否则排产时间、交期、报工时间可能出现偏移。

| 模块 | 目录 | 说明 |

## 5. 数据库与 Redis 部署

### 5.1 使用 docker-compose

```bash
cd jvs-docker-compose
docker-compose -f docker-compose-db.yml up -d
```

默认配置：

| 组件 | 端口 | 账号 |
|------|------|------|
| MySQL | `3306` | `root/root` |
| Redis | `6379` | 密码 `redis` |

### 5.2 初始化数据库

推荐顺序：

1. 导入 `jvs-docker-compose/mysql/jvs-aps.sql`。
2. 如需演示，再导入 `demo-seed.sql`。

### 5.3 数据初始化建议

正式环境不建议直接导入演示数据。推荐流程：

1. 先导结构。
2. 再由实施通过前端录入关键主数据。
3. 或由客户主数据系统导入干净数据。

## 6. 后端部署

### 6.1 关键配置

文件：

`aps/jvs-aps-mgr/src/main/resources/application.yml`

默认项：

| 配置 | 默认值 |
|------|-------|
| 端口 | `31010` |
| context-path | `/mgr/jvs-aps` |
| MySQL | `localhost:3306/jvs-aps` |
| Redis | `localhost:6379` |
| Redis DB | `2` |

### 6.2 本地启动

```bash
cd aps
mvn spring-boot:run -pl jvs-aps-mgr -am
```

### 6.3 打包启动

```bash
cd aps
mvn clean package -DskipTests
java -jar jvs-aps-mgr/target/*.jar
```

### 6.4 Docker 部署

后端 Dockerfile 已存在：

`aps/jvs-aps-mgr/Dockerfile`

当前特点：

1. 基于 Dragonwell 17。
2. 暴露 `31010`。
3. 时区设置为 `Asia/Shanghai`。

正式部署建议补充：

1. `JAVA_OPTS` 内存参数。
2. 环境变量注入 DB/Redis。
3. 健康检查。
4. 持久日志挂载。

## 7. 前端部署

### 7.1 本地开发启动

```bash
cd aps-ui
npm install
npm run dev
```

默认端口：

```text
9998
```

### 7.2 构建

```bash
cd aps-ui
npm run build
```

构建产物输出到：

```text
aps-ui/docker/dist
```

### 7.3 Nginx 镜像

前端 Dockerfile：

`aps-ui/docker/Dockerfile`

当前特点：

1. 使用 `nginx:1.20`。
2. 复制 `dist` 到静态目录。
3. 使用自定义 `nginx.conf` 和 `my.conf`。

正式部署建议：

1. 配置域名和 HTTPS。
2. 为 `/mgr` 配置正确代理。
3. 配置缓存策略。

## 8. 上线前数据准备方案

实施上线时建议分三批准备：

### 8.1 第一批：能让系统跑起来的数据

1. 物料。
2. 资源。
3. 工作模式。
4. 工作日历。
5. 工艺。
6. 工艺路线。
7. BOM。
8. 生产订单。

### 8.2 第二批：让结果更真实的数据

1. 来料计划。
2. 更准确的库存。
3. 更准确的安全库存。
4. 更准确的提前期和缓冲期。
5. 更准确的资源组和设备状态。

### 8.3 第三批：让现场能闭环的数据

1. 派工使用规则。
2. 报工模板。
3. 任务锁定规则。
4. 计划确认流程。

---

## 9. 上线实施顺序

推荐交付顺序：

1. 跑通样例环境。
2. 用真实主数据做单产品族试点。
3. 只接未来 3 到 7 天订单。
4. 做第一次试排。
5. 和业务一起核对结果。
6. 调整主数据和策略。
7. 开始真实派工和报工闭环。
8. 再扩大范围。

不建议一上来就全量历史订单、全车间、全品类同时接入。

---

## 10. 运行检查清单

### 10.1 应用层检查

每天至少检查：

1. 后端服务是否存活。
2. 前端是否可访问。
3. MySQL、Redis 是否连接正常。
4. 日志中是否有排产异常、报工异常。

### 10.2 数据层检查

每天至少检查：

1. 是否有待确认计划长期未处理。
2. 是否有大量未排产订单。
3. 是否有报工导入失败。
4. 是否有任务状态异常。

### 10.3 业务层检查

每日至少检查：

1. 逾期任务数。
2. 锁定任务数。
3. 人工调整次数。
4. 计划放弃率。

## 11. 备份与恢复建议

当前项目未内置备份策略，交付时必须额外提供：

### 11.1 数据库备份

建议：

1. 每日全量备份。
2. 每小时或半天增量备份。
3. 保留最近 7 到 30 天快照。

### 11.2 配置备份

需备份：

1. `application.yml`
2. Nginx 配置
3. 部署脚本
4. 数据初始化脚本

### 11.3 恢复演练

正式上线前至少做一次：

1. 数据库恢复演练。
2. 应用重新发布演练。
3. 前端静态资源回滚演练。

---

## 12. 风险告知模板

实施交付时建议明确书面告知：

### 12.1 产品边界

1. 当前版本更适合单租户场景。
2. 当前版本缺少企业级权限治理。
3. 高级算法参数未全部前台化。

### 12.2 数据边界

1. APS 对数据质量高度敏感。
2. 数据不准时，系统会排出“看似合理、现场不可执行”的计划。

### 12.3 性能边界

1. 排产是 CPU 密集操作。
2. 数据量越大，求解耗时越高。
3. 前端甘特图在任务量很大时会面临渲染压力。

---

## 13. 正式上线前必勾清单

1. MySQL、Redis、后端、前端全部可启动。
2. 数据库结构已初始化。
3. 关键主数据已导入。
4. 关键物料具备 BOM、工艺、路线。
5. 关键资源绑定了工作日历。
6. 至少有一套有效策略。
7. 已演练生成排产。
8. 已演练预览、放弃、提交。
9. 已演练甘特图调整。
10. 已演练派工导出。
11. 已演练报工导入与改单。
12. 已明确业务确认流程。
13. 已完成备份和恢复演练。
14. 已明确客户接受当前版本边界。

---

## 14. 一句话结论

实施与运维交付 JVS-APS 的重点，不是“把服务启动起来”，而是“把数据、流程、监控、风险说明一起交付完整”，否则系统只能算演示可用，不能算上线可用。
