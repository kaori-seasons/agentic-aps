# 第八章：JVS-APS 生产操作手册

> 适用对象：实施顾问、计划主管、排产员、运维人员、开发接手人员  
> 适用版本：当前仓库代码主线  
> 文档目标：把“系统能做什么、怎么部署、怎么准备数据、怎么日常操作、哪里有边界”讲清楚，直接可用于试点上线和生产运行

---

## 1. 手册定位与阅读方式

这份手册不是概念介绍，而是基于当前仓库中的真实实现写成的落地操作说明。它回答四个问题：

1. 当前系统到底已经实现到了什么程度。
2. 企业要怎样准备数据，系统才能排出可执行计划。
3. 计划员在界面里应该按什么顺序使用它。
4. 上线后哪些地方必须治理，哪些地方现在仍然有边界。

建议按以下顺序阅读：

1. 运维和开发先看“部署与运行”。
2. 实施顾问先看“主数据准备”。
3. 计划员先看“排产作业 SOP”。
4. 项目负责人必须看“风险、边界与上线清单”。

## 2. 基于代码的系统结论

### 2.1 当前系统真实具备的能力

结合 `book`、后端代码、前端页面和 SQL，可以确认当前系统已经形成完整闭环：

1. 主数据维护：物料、资源、生产订单、来料计划、制造 BOM、工艺、工艺路线、工作模式、工作日历。
2. 排产求解：支持正排、逆排、物料约束、订单排序规则、OptaPlanner 约束求解。
3. 排产结果管理：先生成待确认计划，再预览、放弃或确认。
4. 结果展示：资源甘特图、订单甘特图、物料需求甘特图、计划任务表。
5. 人工调整：拆分、合并、移动、锁定、解锁、撤销调整。
6. 执行反馈：派工导出、报工导入/改单、任务进度回写、订单排产状态更新。

### 2.2 当前系统的关键实现特征

1. 后端为 `Spring Boot 2.7.12 + Java 17 + MyBatis Plus + Redis + OptaPlanner 9.44.0.Final`。
2. 前端为 `Vue 3 + Vite + Element Plus + @visactor/vtable-gantt`。
3. 排产模型采用 `Planning List Variable` 模式：主资源持有任务列表，任务开始时间由监听器和日历推导。
4. 排产不是“算完即生效”，而是“待确认计划 -> 预览 -> 确认”。
5. 人工锁定任务会作为 `@PlanningPin` 参与后续重排。

### 2.3 当前版本必须直说的边界

这部分必须在实施前讲明白，否则项目会在试点时失真：

1. 租户当前被固定为 `1`。`ContextHolderFilter` 直接把租户写死，不是真正动态多租户。
2. 配置文件当前只有一个 `application.yml`，没有按环境拆分 profile。
3. 前端“策略配置”页面目前只暴露了方向、物料约束、无改进时长、订单排序规则。
4. 后端已支持 `DEFAULT / FFD_TABU / FFD_LATE_ACCEPTANCE`、动态权重、随机种子，但前端当前没有完整暴露这些高级参数。
5. 当前没有看到鉴权、权限隔离、审计追踪等企业级安全治理能力。
6. 求解仍运行在管理服务进程内，未独立成 Worker。

结论很直接：

当前系统已经足够做试点、演示、单工厂场景落地；如果要做严肃生产环境，必须补治理而不是只补文案。

## 3. 系统结构与职责分工

### 3.1 目录结构

| 目录 | 作用 |
|------|------|
| `aps/jvs-aps-common` | 领域模型、求解器、约束、任务调整、报表转换 |

| `book` | 系统书稿与说明文档 |

### 3.2 角色分工建议

| 角色 | 主要职责 |
|------|---------|
| 运维 | 部署 MySQL、Redis、后端、前端；监控进程、磁盘、内存、日志 |

## 4. 部署与启动

### 4.1 环境要求

| 组件 | 要求 |
|------|------|
| JDK | 17 |
| Maven | 3.8+ |
| Node.js | 16.14+ |
| MySQL | 8.0.x |
| Redis | 6.x |
| 操作系统时区 | `Asia/Shanghai` |

### 4.2 数据库与 Redis 启动

项目已提供 `docker-compose-db.yml`，可直接拉起数据库与 Redis。

```bash
cd jvs-docker-compose
docker-compose -f docker-compose-db.yml up -d
```

默认端口与凭据：

| 组件 | 地址 | 默认账号 |
|------|------|---------|
| MySQL | `127.0.0.1:3306` | `root/root` |
| Redis | `127.0.0.1:6379` | 密码 `redis` |

### 4.3 初始化数据库

可选脚本：

1. `jvs-docker-compose/mysql/jvs-aps.sql`：完整表结构初始化。
2. `aps/sql/jvs-aps.sql`：同类结构脚本。
3. `demo-seed.sql`：演示数据，适合本地验收和培训。

推荐顺序：

1. 先导入结构脚本。
2. 需要演示或验证功能时，再导入 `demo-seed.sql`。

### 4.4 后端启动

默认配置在 `aps/jvs-aps-mgr/src/main/resources/application.yml`：

| 项 | 默认值 |
|----|-------|
| 端口 | `31010` |
| context-path | `/mgr/jvs-aps` |
| MySQL | `jdbc:mysql://localhost:3306/jvs-aps` |
| Redis DB | `2` |

启动方式：

```bash
cd aps
mvn spring-boot:run -pl jvs-aps-mgr -am
```

或先打包再运行：

```bash
cd aps
mvn clean package -DskipTests
java -jar jvs-aps-mgr/target/*.jar
```

### 4.5 前端启动

```bash
cd aps-ui
npm install
npm run dev
```

默认访问地址：

| 服务 | 地址 |
|------|------|
| 前端 | `http://localhost:9998` |
| 后端 | `http://localhost:31010/mgr/jvs-aps` |

前端通过 Vite 代理 `/mgr` 到后端。

### 4.6 容器化部署建议

当前仓库已给出后端 Dockerfile 和前端 Nginx Dockerfile，但生产部署前应补：

1. 环境变量化数据库和 Redis 配置。
2. 独立 `dev/test/prod` 配置文件。
3. 日志落盘与滚动策略。
4. 反向代理、域名、HTTPS。
5. 备份与恢复脚本。

## 5. 上线前准备清单

### 5.1 基础设施检查

1. MySQL、Redis 可连接。
2. 应用服务器与数据库时区一致。
3. 服务器 CPU 和内存满足求解需要。
4. 日志目录有写权限。
5. 浏览器端可访问前后端。

### 5.2 数据口径检查

以下任一项缺失，排产都可能“逻辑正确但现场不可执行”：

1. 成品、半成品、原材料编码是否唯一。
2. 生产订单的产品编码是否能映射到物料。
3. 制造类物料是否都有启用中的工艺路线。
4. 工艺路线中的每道工序是否都绑定了可用主资源。
5. 主资源是否绑定了至少一个启用中的工作日历。
6. 来料计划、库存、安全库存口径是否明确。
7. 资源产能格式是否符合系统支持格式。

### 5.3 组织约定

上线前必须约定三件事：

1. 谁可以生成计划。
2. 谁可以确认计划。
3. 锁定任务的业务规则是什么。

如果这三件事不明确，系统即使能排，也会陷入频繁重算和计划互相覆盖。

## 6. 主数据准备 SOP

建议严格按以下顺序录入。

### 6.1 物料

页面：`物料`

必填关键信息：

1. 编码、名称、类型。
2. 来源：`PRODUCED` 或 `PURCHASED`。
3. 当前库存与安全库存。
4. 单位。
5. 提前期、缓冲期。

实施原则：

1. 所有会被排产的成品和半成品必须是 `PRODUCED`。
2. 所有采购件应设为 `PURCHASED`。
3. 提前期和缓冲期建议先从保守值开始，不要填成 0。

### 6.2 主资源

页面：`主资源`

必填关键信息：

1. 编码、名称、资源组。
2. 容量与单位。
3. 产能。
4. 资源状态：正常、维修、报废。

注意：

1. 只有 `NORMAL` 资源会参与排产。
2. 产能是排产时间计算的核心，格式必须正确。

### 6.3 来料计划

页面：`来料计划`

作用：

1. 为采购件补充未来可用量。
2. 与库存一起决定是否触发欠料。

建议：

1. 只录入真实在途、可预期到货的采购件。
2. 状态为 `PROCESSING` 的来料单才会参与 MRP。

### 6.4 制造 BOM

页面：`制造 BOM`

作用：

1. 定义物料依赖关系。
2. 决定订单拆解时的欠料传导链。

建议：

1. 先从成品 BOM 做起，再逐步补齐半成品 BOM。
2. 单位换算必须业务确认后再录。
3. 没有 BOM 的制造件在物料约束模式下会直接影响任务生成质量。

### 6.5 工艺

页面：`工艺`

每道工艺需维护：

1. 工序编码、名称。
2. 工序关系：`ES` 或 `EE`。
3. 前间隔、后间隔、缓冲时间。
4. 可用主资源及其产能。
5. 使用物料。

实际含义：

1. `ES`：前工序结束后，后工序再开始。
2. `EE`：后工序可以与前工序形成重叠约束。

### 6.6 工艺路线

页面：`工艺路线`

作用：

1. 把工艺节点和先后依赖组织成 DAG。
2. 按物料维度定义完整制造路径。

上线要求：

1. 同一制造物料必须至少有一条启用中的工艺路线。
2. 工艺路线节点中的资源能力必须与资源主数据一致。
3. 试点阶段先避免过于复杂的并行路线，先保证稳定可解释。

### 6.7 工作模式与工作日历

页面：`生产日历`

工作模式定义：

1. 一天内的工作时间段，如 `08:00-12:00, 13:00-17:00`。

工作日历定义：

1. 生效起止日期。
2. 星期工作日设置。
3. 绑定工作模式。
4. 关联资源。

注意：

1. 不绑定日历时，系统会退化为自然时间推导。
2. 想让排产贴近现场，必须优先把日历建准。

### 6.8 生产订单

页面：`生产订单`

关键信息：

1. 订单号。
2. 产品编码。
3. 数量。
4. 需求日期。
5. 优先级。
6. 是否允许排产。

建议：

1. 需求日期必须真实，否则逆排和逾期评估没有意义。
2. 优先级要形成企业统一口径，例如 `P1` 最高，`P5` 最低。
3. 试点初期只放一段时间窗口内的订单，不要一次把全年订单全灌入。

## 7. 排产策略配置 SOP

页面：`排产策略`

### 7.1 前端当前可配置项

当前界面已暴露：

1. 策略名称。
2. 开始时间。
3. 排产方向。
4. 无改进时长。
5. 是否约束物料。
6. 订单排序规则。
7. 是否生效。

### 7.2 后端已支持但前端未完整暴露的能力

代码中已支持：

1. `DEFAULT`
2. `FFD_TABU`
3. `FFD_LATE_ACCEPTANCE`
4. 约束权重配置
5. 随机种子
6. 禁忌长度、晚期接受缓存、acceptedCountLimit

如果项目进入正式生产阶段，建议开发补充“高级策略配置”页面，否则很多算法能力只能停留在 DTO 层。

### 7.3 推荐策略模板

| 模板 | 方向 | 物料约束 | 适用场景 |
|------|------|---------|---------|
| 标准排产 | FORWARD | 开 | 日常滚动排产 |
| 交期优先 | BACKWARD | 开 | 客户交期压得紧 |
| 快速评估 | FORWARD | 关 | 先看资源大体负载 |

### 7.4 排产规则建议

默认排序逻辑接近：

1. 高优先级优先。
2. 交期近的优先。

建议不要在试点初期加太多规则字段，否则会让业务难以解释结果。

## 8. 排产作业 SOP

页面：`排产计划`

### 8.1 正常作业流程

1. 进入“排产计划”页面。
2. 点击顶部“生成排产”。
3. 选择一个生效中的策略。
4. 发起排产。
5. 观察进度条和日志。
6. 排产完成后点击“预览”。
7. 先看资源甘特图，再看订单甘特图和物料需求图。
8. 如果结果可接受，点击“提交”确认计划。
9. 如果结果不可接受，点击“放弃”。

### 8.2 系统内部实际行为

发起排产后，系统会依次执行：

1. 检查是否已有进行中的排产。
2. 检查是否已有待确认计划。
3. 读取当前基础数据快照。
4. 执行 MRP。
5. 生成任务链。
6. 装配 `SchedulingSolution`。
7. 异步求解。
8. 保存到待确认任务表和待确认订单表。

### 8.3 进度状态解释

| 状态 | 含义 |
|------|------|
| `NONE` | 当前没有排产进度 |
| `SCHEDULING` | 求解进行中 |
| `SUCCESS` | 已形成待确认计划 |
| `NO_SCHEDULED` | 没有需要排的任务 |
| `FAILURE` | 求解失败或校验失败 |

### 8.4 预览时要重点看什么

资源甘特图重点看：

1. 瓶颈资源是否过载。
2. 是否出现明显不合理空档。
3. 高优先级任务是否被压后。

订单甘特图重点看：

1. 末工序结束时间是否超过交期。
2. 同一订单工序链是否断裂。

物料需求甘特图重点看：

1. 未来几天是否集中拉动某类物料。
2. 是否可能引发采购或仓储压力。

计划任务表重点看：

1. 是否有未分配资源的任务。
2. 是否存在异常拆分、异常合并、异常数量。

## 9. 人工调整 SOP

页面：`资源甘特图`

### 9.1 当前支持的操作

1. 撤销调整。
2. 按数量拆分。
3. 按任务数量平均拆分。
4. 按完成数量拆分。
5. 合并选中任务。
6. 移动任务位置。
7. 移动部分完成任务进度。
8. 锁定指定任务。
9. 锁定已开工任务。
10. 解锁指定任务。
11. 解锁已开工任务。
12. 报工导入。
13. 派工导出。

### 9.2 推荐调整顺序

不要看到不满意就直接大改，建议按下面顺序：

1. 先锁定已开工任务。
2. 再锁定业务上绝不能动的关键订单任务。
3. 再处理局部拥堵资源。
4. 最后才做拆分、合并、移动。

### 9.3 什么情况下该拆分

适合拆分的场景：

1. 一个大任务要分批流转。
2. 现场已经部分完工。
3. 需要把剩余任务分散到多个时间段。

不适合拆分的场景：

1. 工艺本身不允许分批。
2. 任务本来就是短节拍，不值得切碎。

### 9.4 什么情况下该合并

适合合并的场景：

1. 多个任务本质上可以视作一个执行批次。
2. 现场希望减少换线、换刀、换模次数。

注意：

1. 合并是强业务动作，不应作为“看着乱就合一下”的 UI 修饰手段。

### 9.5 锁定原则

建议采用“三层锁定规则”：

1. 自动锁：已开工任务默认锁。
2. 业务锁：关键订单、客户承诺任务手工锁。
3. 临时锁：本班次内已发派工的任务锁。

### 9.6 撤销机制的真实含义

当前“撤销调整”：

1. 会撤回移动、拆分、合并。
2. 不撤回锁定/解锁状态。

所以锁定动作要谨慎，它不是临时草稿，而是更高等级的业务决定。

## 10. 计划确认、派工与报工

### 10.1 确认计划

确认后会发生：

1. 待确认任务写入正式 `jvs_plan_task`。
2. 待确认订单写入正式 `jvs_plan_task_order`。
3. 清理待确认数据。
4. 清理已调整任务缓存。
5. 更新计划基本信息。

注意：

1. 如果存在调整，锁定任务的调整将保留，未锁定的调整会被清空。

### 10.2 派工

页面入口：资源甘特图中的“派工”

后端行为：

1. 根据派工时间窗口，截取区间内未完成任务。
2. 按资源和工作日历生成派工计划。
3. 导出 Excel。

使用建议：

1. 派工窗口不要过长，建议按班次、天或滚动两天处理。
2. 派工前先确认计划已提交。

### 10.3 报工

页面入口：资源甘特图中的“报工”

支持方式：

1. Excel 导入。
2. 单任务修改。
3. 批量修改。

报工校验逻辑会检查：

1. 订单号。
2. 工序编码。
3. 计划资源编码。
4. 计划开始时间。
5. 报工时间。
6. 完成数量不能为负。
7. 同一条报工不能重复。

### 10.4 报工后的系统联动

1. 更新任务已完成数量。
2. 更新任务状态：未完成、部分完成、已完成。
3. 若任务是合并任务子任务，会同步汇总到合并任务。
4. 更新订单排产状态。

## 11. 运行治理建议

### 11.1 每日例行操作

计划员建议每日执行：

1. 核对前一日报工是否全部回写。
2. 核对今日新订单和交期变更。
3. 核对关键资源状态。
4. 核对来料计划更新。
5. 再做排产。

### 11.2 每周治理动作

实施/主管建议每周执行：

1. 检查异常多的人工调整。
2. 统计锁定任务比例。
3. 检查高频拖期订单。
4. 核对资源日历是否和现场班次一致。
5. 复盘策略是否需要分场景切换。

### 11.3 推荐监控指标

| 类别 | 指标 |
|------|------|
| 求解 | 单次排产耗时、失败率、取消率 |
| 结果 | 逾期任务数、逾期订单数、资源冲突数 |
| 人工干预 | 拆分次数、移动次数、锁定数量、撤销次数 |
| 生产执行 | 报工延迟率、计划达成率、已完成任务占比 |

## 12. 已知风险与应对

### 12.1 数据风险

| 风险 | 表现 | 应对 |
|------|------|------|
| 工艺路线缺失 | 订单不能正常拆解成任务 | 上线前做物料-路线覆盖率检查 |
| 资源产能格式错误 | 时间计算异常或报错 | 上线前抽样验证每类产能格式 |
| 日历不准 | 计划跨休息时间、现场无法执行 | 日历先和班组长核对 |
| BOM 不完整 | 欠料逻辑失真 | 分层补齐，先做关键产品族 |

### 12.2 算法与使用风险

| 风险 | 表现 | 应对 |
|------|------|------|
| 权重或策略不合理 | 结果看起来“能排但不顺手” | 先用少量模板，不要一开始开放全部高级参数 |
| 重排蝴蝶效应 | 人工调整后一重算全乱 | 先锁定已开工和关键任务 |
| 数据量过大 | 求解变慢、前端卡顿 | 先按时间窗口排产，不要全量历史订单一起跑 |

### 12.3 平台治理风险

| 风险 | 现状 | 建议 |
|------|------|------|
| 多租户 | 当前固定租户 `1` | 正式上线前改为真实租户上下文 |
| 环境配置 | 当前单一 `application.yml` | 拆分 profile 和环境变量 |
| 权限审计 | 当前未体现 | 补登录、权限、操作日志 |
| 求解隔离 | 当前与管理服务同进程 | 中长期拆为独立求解 Worker |

## 13. 自我辩证与反思

这部分不是客套，而是项目落地必须有的自我校准。

### 13.1 这套系统最强的地方

1. 不是简单 CRUD，而是真正把主数据、求解、预览、调整、确认、派工、报工串起来了。
2. 使用 OptaPlanner 和 List Variable 模型，说明系统不是靠硬编码排序脚本凑出来的。
3. “待确认计划 + 甘特图调整 + 锁定重排”这条链路非常符合真实工厂。

### 13.2 这套系统当前最脆弱的地方

1. 平台治理层明显弱于业务功能层。
2. 高级策略虽然在后端具备，但前端还没有真正产品化。
3. 当前默认单租户、本地配置、同进程求解，更像可落地原型而不是最终企业平台。

### 13.3 最容易犯的误判

1. 误判一：样例能排出结果，就等于已经准备好上线。
2. 误判二：算法结果不好，一定是求解器问题。
3. 误判三：只要多加约束，结果一定更贴近现场。

正确理解应当是：

1. APS 成败首先取决于数据治理，其次才是算法调优。
2. 算法不是替代计划员，而是给计划员提供高质量基线。
3. 约束越多不一定越好，错误约束只会让系统更难解释。

## 14. 试点上线建议路径

建议分四步推进：

### 第一阶段：演示验证

1. 使用 `demo-seed.sql`。
2. 验证部署、排产、预览、确认、派工、报工全链路。

### 第二阶段：单产品族试点

1. 只选一个产品族。
2. 只选关键资源。
3. 只排未来 3 到 7 天。

### 第三阶段：单车间正式运行

1. 引入真实班次和订单。
2. 每日滚动排产。
3. 开始统计人工调整比例。

### 第四阶段：平台化增强

1. 拆 Worker。
2. 补权限。
3. 补多租户。
4. 补高级策略 UI。
5. 补快照复盘与策略对比。

## 15. 最终上线清单

正式上线前，逐项勾选：

1. MySQL、Redis、后端、前端可稳定启动。
2. 结构脚本与基础数据已初始化。
3. 关键物料都有来源、库存、安全库存、提前期、缓冲期。
4. 关键制造件都有启用中的工艺路线。
5. 关键工艺都配置了可用主资源和正确产能。
6. 关键资源都绑定了有效日历。
7. 生产订单字段口径统一。
8. 至少准备 3 套排产策略模板。
9. 已定义锁定任务规则。
10. 已演练“生成 -> 预览 -> 调整 -> 确认 -> 派工 -> 报工”闭环。
11. 已确认谁有确认计划权限。
12. 已确认数据库备份与日志策略。
13. 已确认多租户、权限、环境配置边界被业务接受，或已安排开发补齐。

---

## 16. 一句话结论

当前 JVS-APS 已经具备“可排、可看、可调、可确认、可派工、可报工”的完整业务闭环，适合试点和单工厂落地；但若要进入严肃生产环境，必须把数据治理、策略治理和平台治理同步补齐，不能把业务功能完整误判成生产能力完整。
