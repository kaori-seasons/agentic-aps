# 第十二章：多租户与角色权限生产化排期计划

> 归档日期：2026-04-26  
> 计划起点假设：2026-04-27  
> 适用对象：产品负责人、项目经理、架构师、后端、前端、测试、实施、运维  
> 目标：基于当前仓库真实代码现状，形成一份可用于生产推进的多租户与角色权限实施计划

---

## 1. 先给结论

当前仓库**不适合直接按“多租户 + 多角色 + 生产治理”标准上线**，但它并不是从零开始。

现状更准确的判断是：

1. **它已经有一套“伪多租户骨架”**。
2. **它还没有“真实租户上下文”**。
3. **它基本没有 APS 业务角色权限闭环**。
4. **它缺少审计、灰度、数据回填、跨线程上下文治理这些生产必需项**。

因此，本次建设不应被定义为“补几个权限按钮”，而应定义为：

**把单租户试点版 APS，升级成共享库共享表的真实租户隔离版 APS，并补齐计划主管、排产员、生产调度员三类角色的权限闭环。**

我建议的一期目标不是“做成完全 SaaS 平台”，而是先完成：

1. 真实租户上下文。
2. APS 角色权限矩阵。
3. 组织数据范围控制。
4. 审计与上线治理。

在资源投入正常的前提下，**主计划周期建议为 10 周**，对应日历区间为：

`2026-04-27` 到 `2026-07-03`

如果上游已经有统一登录、统一租户中心、统一角色中心，可按 10 周执行。  
如果这些能力都没有，且要在 APS 仓库内自建最小权限中心，建议**额外增加 2 周**。

## 2. 本计划基于哪些事实

本计划不是抽象建议，而是基于 `book/` 文档与当前代码的交叉核对。

### 2.1 文档侧结论

`book/08_production_operations_manual.md`、`book/10_implementation_operations_manual.md`、`book/11_developer_handover_manual.md` 已经反复给出明确边界：

1. 当前租户固定为 `1`。
2. 当前没有完整鉴权与权限体系。
3. 当前更适合单工厂、单租户试点。

`book/09_business_planner_manual.md` 又明确提出了业务角色：

1. 计划主管。
2. 排产员。
3. 生产调度员。

这说明业务手册已经进入“分角色操作”的阶段，但系统实现还停留在“功能几乎全开”的阶段。

### 2.2 代码侧结论

后端已经预留了多租户基础设施：

1. SQL 的 19 张核心表都带 `tenant_id`。
2. MyBatis Plus 已启用 `TenantLineInnerInterceptor`。
3. `SolveManageConfigurator` 用 `Map<tenantId, SolverManager>` 管理求解器。
4. `SolveProgressServiceImpl` 的 Redis key 按租户隔离。
5. 待确认计划、调整记录等部分实体已经显式持有 `tenantId`。

但真正的入口层仍然是单租户：

1. `ContextHolderFilter` 直接把租户写死为 `"1"`。
2. 后端控制器没有发现权限注解或统一鉴权切面。
3. 依赖中没有看到 `Spring Security`、`Sa-Token`、`Shiro`、`OAuth/JWT` 等成体系安全框架。
4. 前端 APS 路由全部 `isAuth: false`。
5. 前端菜单 `permisionFlag` 全为空字符串。
6. 前端请求层没有把 `tenantId` 写入请求头。

还有一个隐藏但关键的生产风险：

1. 排产主流程 `SolveServiceImpl.solve(...)` 使用 `@Async`。
2. `TenantContextHolder` 底层虽然用了 `TransmittableThreadLocal`。
3. 但当前代码没有看到显式的 `TaskDecorator`、TTL 包装执行器或异步线程池治理。

在租户固定为 `1` 的情况下，这个问题不会暴露。  
一旦租户改成动态，这里很可能变成跨线程串租户风险点。

## 3. 先做一个自我辩证

### 3.1 “手册里有三个角色”不等于“必须立刻做真多租户”

如果业务目标只是一个工厂内部的三类岗位分工，那么严格来说，**先做 RBAC 也能解决一半问题**。

例如：

1. 计划主管能确认计划。
2. 排产员能生成、预览、调整。
3. 生产调度员能派工、报工。

仅从这个层面看，做角色权限就够了。

### 3.2 但如果只做 RBAC，不做真实租户，会留下更大的后患

原因有三点：

1. 数据库、求解器、Redis 已经按租户预留了结构，说明系统设计方向本来就不是纯单租户。
2. 现在租户被写死成 `1`，本质上是在掩盖隔离问题，而不是解决隔离问题。
3. 一旦后续再补多租户，角色权限、审计、报表、待确认计划、异步求解都要重验一遍，返工成本更高。

### 3.3 结论

本次工作不应拆成“先角色，后租户”的两条完全独立项目线。  
更合理的做法是：

1. **第一优先级先打通真实租户上下文**。
2. **第二优先级在此基础上做 APS 角色权限矩阵**。
3. **第三优先级补审计、灰度、迁移和上线治理**。

### 3.4 另一个需要克制的点

也不建议一期就追求：

1. 每租户独立数据库。
2. 求解器独立 Worker 集群。
3. 字段级权限。
4. 审批流引擎。
5. 完整 IAM 子系统自研。

原因很直接：  
当前代码已经是**共享库共享表 + `tenant_id` 行级隔离**的形态，一期最小可行生产方案应该沿这条路继续，而不是把问题扩大成平台重构。

## 4. 现状评估

| 维度 | 当前评级 | 判断 |

| 审计追踪 | D | 关键操作未形成可追责闭环 |

## 4.2 当前已经能复用的资产

这部分决定了为什么我建议做 10 周，而不是 4 个月：

1. `tenant_id` 已在 SQL 层普遍存在。
2. MyBatis 租户拦截器已接入。
3. 求解器、进度、待确认计划已按租户思路设计。
4. 前端已有 `tenantId`、`tenantInfo`、`permisionFlag` 这类通用骨架。
5. APS 业务流程已经完整，缺的是治理，不是缺主业务能力。

## 4.3 当前必须补的短板

这部分是本次排期的真正工作量来源：

1. HTTP 入口租户上下文动态化。
2. 用户身份、角色、组织范围上下文。
3. 后端接口鉴权。
4. 前端菜单、按钮、路由、页面动作权限控制。
5. 关键业务动作审计。
6. 历史数据 `tenant_id` 回填与脏数据校验。
7. `@Async` 排产链路租户上下文传播验证。
8. 上线灰度、回滚与压测方案。

## 5. 一期目标架构

## 5.1 技术路线

一期建议采用：

**共享数据库、共享表、`tenant_id` 行级隔离、租户上下文 + RBAC + 数据范围控制**

这是和当前项目最一致、改造成本最低、最可能按期落地的路线。

## 5.2 统一上下文模型

后端请求进入后，必须统一解析出以下上下文：

1. `tenantId`
2. `userId`
3. `username`
4. `roleCodes`
5. `factoryIds`
6. `workshopIds`
7. `resourceGroupIds`

建议新增统一认证上下文，例如：

`AuthContextHolder`

`TenantContextHolder` 不再单独承担全部责任，而是退化为 `AuthContext` 的一个子视图。

## 5.3 角色模型

一期只做 APS 最核心三类角色，加一个系统管理员：

| 角色 | 角色编码建议 | 定位 |
|------|-------------|------|
| 系统管理员 | `APS_ADMIN` | 租户内基础配置、角色授权、运维治理 |
| 计划主管 | `APS_PLAN_MANAGER` | 策略生效、生成审批、确认计划、锁定规则、结果审核 |
| 排产员 | `APS_SCHEDULER` | 生成、预览、人工调整、局部操作 |
| 生产调度员 | `APS_DISPATCHER` | 派工导出、报工导入、任务进度回写、现场查看 |

## 5.4 数据范围模型

角色之外，还必须叠加组织范围，否则多工厂场景仍然不够用。

建议范围层级：

1. 租户。
2. 工厂。
3. 车间。
4. 资源组。

### 建议原则

1. 计划主管默认到工厂级。
2. 排产员默认到车间或资源组级。
3. 生产调度员默认到资源组级。
4. 系统管理员到租户级。

## 7.2 P0 方案冻结

### 目标

把“做什么”和“不做什么”一次说清，避免中途扩 scope。

### 任务

1. 冻结一期租户模型：共享库共享表，不做分库分租户。
2. 冻结角色模型：`APS_ADMIN`、`APS_PLAN_MANAGER`、`APS_SCHEDULER`、`APS_DISPATCHER`。
3. 冻结组织范围模型：工厂、车间、资源组。
4. 确认身份来源：
   如果上游已有网关或用户中心，则约定请求头或 JWT Claim。
5. 冻结接口契约：
   约定 `tenantId`、`userId`、`roleCodes`、`scope` 的传递方式。
6. 输出现网数据摸底清单：
   核对 19 张表 `tenant_id` 非空率与重复编码风险。

### 交付物

1. 权限矩阵表。
2. 数据范围矩阵表。
3. 接口上下文契约文档。
4. 历史数据摸底报告。

### 验收口径

1. 业务、开发、测试、实施对角色职责没有分歧。
2. 上游身份接入方式明确。
3. 任何新增需求若超出一期边界，统一进入二期池。

## 7.3 P1 租户上下文打通

### 目标

把系统从“伪多租户”改成“真实多租户”。

### 任务

1. 改造 `ContextHolderFilter`：
   不再写死 `"1"`，改为从请求头、网关透传或 JWT 中解析租户与用户信息。
2. 新增统一认证上下文对象：
   包含 `tenantId`、`userId`、`roleCodes`、`scope`。
3. 改造前端请求层：
   统一携带租户上下文或接入现有宿主平台注入机制。
4. 增加缺省保护：
   没有租户、用户、角色时直接拒绝访问，而不是默认放行。
5. 补异步上下文治理：
   为 `@Async` 执行链补 `TaskDecorator` 或 TTL 包装执行器验证，确保排产线程拿到正确租户。
6. 验证 Redis key、求解器实例、待确认计划在多租户下是否完全隔离。

### 交付物

1. 动态租户入口改造代码。
2. 认证上下文组件。
3. 异步上下文传播验证报告。

### 验收口径

1. 租户 A、租户 B 使用同样订单编码时，互不可见。
2. 两个租户可并行发起排产，Redis 进度互不污染。
3. 排产线程、导出线程、报工线程不会串租户。

## 7.4 P2 后端权限与数据范围

### 目标

后端先收口，防止前端只是“隐藏按钮”但接口仍可直调。

### 任务

1. 引入统一鉴权机制：
   可基于 AOP、拦截器或成熟安全框架进行接口权限校验。
2. 在控制器层或 facade 层加动作权限声明。
3. 为 `SmartSchedulingController`、`PlanningStrategyController`、`TaskAdjustController`、`TaskAssignmentController`、`TaskReportController`、`ScheduleResultController` 建立最小权限映射。
4. 加数据范围控制：
   工厂、车间、资源组过滤不允许只留在前端。
5. 增加关键操作审计：
   生成排产、放弃、确认、拆分、合并、移动、锁定、派工导出、报工导入、报工修改。
6. 增加异常审计：
   权限拒绝、越权访问、跨租户访问尝试。
7. 梳理核心查询与写入 SQL，确认都受租户拦截器与数据范围控制。

### 交付物

1. 权限注解或权限切面。
2. 数据范围过滤器。
3. 审计日志表与查询接口。

### 验收口径

1. 排产员不能确认计划。
2. 生产调度员不能修改策略。
3. 非授权工厂用户看不到别的工厂计划。
4. 所有关键动作都有审计记录。

## 7.5 P3 前端权限闭环

### 目标

把后端已经收口的权限，在前端工作台真正体现出来。

### 任务

1. 改造路由：
   APS 页面不再全部 `isAuth: false`。
2. 改造菜单：
   `localMenu.js` 中的 `permisionFlag` 补齐。
3. 改造按钮与操作入口：
   生成、预览、提交、拆分、合并、移动、锁定、派工、报工等按钮按角色显示。
4. 改造页面内状态：
   对“只读用户”禁用拖拽、调整、导入、导出、策略生效等动作。
5. 增加无权限提示与降级行为。
6. 增加租户切换后的状态清理：
   页面缓存、进度轮询、待确认计划缓存、标签页状态必须清空。

### 交付物

1. 前端权限指令或权限工具。
2. 菜单权限配置。
3. APS 工作台角色化界面。

### 验收口径

1. 不同角色登录后看到不同菜单与按钮。
2. 租户切换后旧租户数据不会残留在页面。
3. 前端页面行为与后端权限结果一致。

## 7.6 P4 数据迁移与联调验收

### 目标

让改造后的系统可以平稳接住现有数据，而不是只在空库里通过测试。

### 任务

1. 生成 `tenant_id` 回填脚本。
2. 校验 19 张业务表 `tenant_id` 非空率。
3. 校验租户内唯一性：
   例如物料编码、任务编码、订单编码是否满足“租户内唯一”。
4. 增加脏数据修复脚本。
5. 做联调用例：
   多租户并发排产、跨角色操作、跨范围访问拒绝。
6. 做压测：
   至少验证 3 个租户并发排产与导出、报工、查询混合场景。
7. 输出 UAT 用例与上线清单。

### 交付物

1. 数据回填脚本。
2. 脏数据整改清单。
3. UAT 报告。
4. 上线执行手册。

### 验收口径

1. 历史数据无跨租户污染。
2. 核心业务用例全部通过。
3. 并发场景下无明显串租户、误授权、死锁问题。

## 7.7 P5 灰度与试运行

### 目标

先试点，再放量，不做一次性全量切换。

### 任务

1. 选 1 个租户、1 个工厂做灰度。
2. 首周只开放：
   查看、生成、预览、派工、报工。
3. 第二周再开放：
   人工调整、确认计划、审计查询。
4. 每日检查：
   排产成功率、越权告警、审计完整性、用户反馈。
5. 收敛问题后形成正式放量评审。

### 交付物

1. 灰度日报。
2. 问题清单与修复单。
3. 正式放量建议书。

### 验收口径

## 9. 必须明确的技术决策

## 9.1 建议立即确定

1. 上游身份源是否存在。
2. 权限模型是否复用集团或平台统一角色中心。
3. 数据范围是否按工厂/车间/资源组三级落地。
4. 审计日志保留周期。
5. 试点租户名单。

## 9.2 不建议一期解决

1. 分库分租户。
2. 求解器独立微服务化。
3. 字段级权限。
4. 完整审批流。
5. 跨租户运营后台。

## 9.3 一个容易误判的点

当前只有部分 PO 显式定义了 `tenantId` 字段，而 SQL 的 19 张表几乎都有 `tenant_id`。

这件事不必在一期被误解成“所有 PO 都要全面重构”。

更合理的处理是：

1. 一期保证租户拦截、写入回填、查询隔离、审计追踪全部正确。
2. 对直接依赖 `tenantId` 业务条件的核心对象继续保留显式字段。
3. 对其余 PO 是否补字段，放入二期整洁性治理。

这是一个工程上的克制，不是偷工减料。

## 11. 上线门槛

只有同时满足以下条件，才建议从试点转生产：

1. 动态租户上下文已替代写死租户。
2. 角色矩阵已在前后端同时生效。
3. 工厂/车间/资源组数据范围已生效。
4. 排产异步链路已验证不会串租户。
5. 关键动作审计可查。
6. 历史数据 `tenant_id` 已回填完成。
7. 至少完成 1 个租户、5 个工作日灰度运行。

如果以上条件有任意一项未满足，我的建议都不是“带风险上线”，而是：

**继续按单租户试点版运行，不要提前宣称已经具备企业级多租户能力。**

---

## 12. 最终建议

对这个项目，最重要的不是“补一个多租户开关”，而是**纠正建设顺序**。

正确顺序应该是：

1. 真实租户上下文。
2. 角色与数据范围。
3. 审计与灰度。
4. 之后再考虑求解器服务拆分、行业模板深化、平台化运营。

基于当前仓库，我给出的生产建议是：

1. 一期按 **10 周** 执行。
2. 技术路线选 **共享库共享表 + `tenant_id` 行级隔离**。
3. 角色先收敛到 **计划主管、排产员、生产调度员、系统管理员** 四类。
4. 不把求解器拆服务放进一期。
5. 不把分库分租户放进一期。

如果按这个节奏推进，JVS-APS 可以从“单租户可试点原型”，升级到“具备真实租户隔离、角色边界和上线治理的一期生产版”。
