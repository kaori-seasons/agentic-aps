# 第一章：JVS-APS 的业务场景与系统架构基础

## 总论：从“人工排表”到“约束驱动排产”

制造企业的排产工作，表面上是在安排订单，实质上是在处理一个持续变化的多约束博弈问题：

```
客户交期越来越紧
        vs
设备、人员、物料、工艺都有限
```

如果只靠 Excel、经验表和人工计划员，系统很快会碰到三个瓶颈：

1. **约束太多**：订单交期、资源能力、工艺前后置、工作日历、补料、插单，任何一个维度都会让简单排序规则失效。
2. **变化太快**：上午刚排好的计划，下午可能就因为设备故障、紧急订单、工序拖期而局部失真。
3. **协同太难**：算法要给出解，但计划员也必须能看懂、能干预、能锁定关键任务。

JVS-APS 的目标不是做一个“自动生成列表”的系统，而是构建一个完整的 **高级计划与排程平台**：从主数据准备，到求解器建模，到甘特图交互，再到人工调整后的确认落库，形成闭环。

---

## 一、JVS-APS 解决什么问题

### 1.1 四类核心业务场景

#### **场景一：常规订单排产**

企业需要把一批生产订单按优先级、交期和资源能力排入未来时间轴。这里的难点不是“按顺序排”，而是：

- 同一设备不能时间重叠
- 同一订单的多道工序不能乱序
- 工作日历决定了可生产时段
- 资源能力决定了任务是否可分配

#### **场景二：紧急插单**

一张高优先级订单突然进入系统。此时不能简单把它插到最前面，因为插单会同时影响：

- 原有订单的交付承诺
- 瓶颈设备的占用
- 后续工序的衔接关系
- 已经人工锁定的任务安排

#### **场景三：现场调整后的局部重排**

计划员可能已经在甘特图上完成了部分人工修正，例如：

- 锁定已开工任务
- 把任务移动到指定资源
- 按完成数量拆分任务
- 对局部任务进行合并

这时重新排产必须尊重人的调整意图，而不能“一键重算后全部打乱”。

#### **场景四：多视角结果查看**

计划结果不是只给算法看，系统至少要支持三种视角：

| 视角 | 目标 | 系统实现 |
|------|------|---------|
| 资源视角 | 看每台设备何时干什么 | 资源甘特图 |
| 订单视角 | 看订单在哪些工序上推进 | 订单甘特图 |
| 物料视角 | 看未来物料需求节奏 | 物料需求甘特图 |

## 二、当前系统的总体结构

### 2.1 代码级架构

当前仓库中的系统结构可以概括为：

```
┌──────────────────────────────────────────────┐
│                 前端 aps-ui                  │
│  数据台账 / 工艺路线 / 排产策略 / 甘特图     │
└──────────────────┬───────────────────────────┘
                   │ HTTP
┌──────────────────▼───────────────────────────┐
│              jvs-aps-mgr 管理层              │
│ controller：生成排产、查看进度、预览、确认   │
└──────────────────┬───────────────────────────┘
                   │ service / facade
┌──────────────────▼───────────────────────────┐
│            jvs-aps-common 核心能力层         │
│  主数据、任务生成、约束求解、报表转换         │
└──────────────────┬───────────────────────────┘
                   │ OptaPlanner
┌──────────────────▼───────────────────────────┐
│               solve 排产求解引擎             │
│  SchedulingSolution / ProductionTask / Score │
└──────────────────────────────────────────────┘
```

### 2.2 三个最重要的系统模块

#### **模块一：基础数据与工程定义**

前端路由中已经明确拆出三块业务域：

- `dataBase`：物料、资源、生产订单、来料计划、制造 BOM
- `productionEngineering`：工艺、工艺路线、生产日历
- `programOfProduction`：排产策略、排产计划

这说明系统不是“只管求解”的黑盒，而是要求企业先把生产世界结构化表达出来。

#### **模块二：排产求解引擎**

在 `cn.windwheel.aps.solve` 包下，系统已经具备完整求解要素：

- `SchedulingSolution`：规划解
- `ProductionTask`：排产实体
- `MainProductionResource`：承载任务列表的资源实体
- `ApsHardSoftScoreConstraintProvider`：约束评分器
- `SolveManageConfigurator`：求解器装配器
- `SolveServiceImpl`：排产执行入口

#### **模块三：可视化与人工干预**

前端 `productionSchedulingPlan` 页面不是简单报表，而是一个完整的交互式工作台：

- 查询待排订单
- 发起智能排产
- 轮询排产进度
- 预览结果
- 确认或放弃计划
- 在资源甘特图上继续拆分、合并、移动、锁定任务

## 三、为什么这套架构适合 APS

### 3.1 不是 CRUD 系统，而是“求解型系统”

普通业务系统的核心是表单、列表和状态流转。APS 不一样，它的核心能力是：

1. 把真实工厂抽象为一组可计算的事实与变量
2. 把排程目标表达为硬约束和软约束
3. 在巨大解空间中搜索一个可行且尽量优的解

这就是为什么当前系统选择了 **Spring Boot + OptaPlanner + Vue 甘特图** 这条路线，而不是只写一堆 if/else 排序脚本。

### 3.2 三个关键设计决策

**决策一：用 OptaPlanner 建模，而不是手工贪心排序**

- **为什么**：排产天然是 NP-Hard 问题，任务规模一旦上来，单一规则会迅速失效
- **好处**：可以把“资源不重叠”“工序前后置”“尽量不逾期”等目标放进同一框架
- **代价**：建模复杂，调参门槛高

**决策二：保留计划员干预能力**

- **为什么**：现场总有未建模的隐性约束
- **好处**：通过锁定、移动、拆分、合并让计划员与算法协作
- **代价**：必须处理重排时的“蝴蝶效应”

**决策三：把策略配置独立出来**

- **为什么**：不同企业关注的目标不同，有的更关心交期，有的更关心换型成本
- **好处**：求解方向、终止条件、权重、策略模板都能配置
- **代价**：需要给实施人员更强的策略理解能力

## 五、本章小结与下章预告

### 核心收获

1. **JVS-APS 的本质**：不是订单列表工具，而是约束求解驱动的生产计划系统。
2. **系统主线**：基础数据建模 → 求解 → 预览 → 人工干预 → 确认落库。
3. **架构特征**：后端以求解器为核心，前端以甘特图为核心，二者通过策略与计划状态连接。

### 关键数字

- 前端核心排产页面主标签：5 个
- 结果预览标签：4 个
- 排产进度轮询周期：2 秒
- 当前内置求解策略模板：3 种

### 下章预告

第二章将进入 **领域建模与基础数据层**：订单、BOM、工艺、资源、日历这些对象，究竟是如何一步步被翻译成 `SchedulingSolution` 中可求解的数据结构的。
