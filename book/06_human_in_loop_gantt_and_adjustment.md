# 第六章：人机协同、甘特图与任务调整——从自动排产到可执行计划

## 总论：最好的排产系统，不是替代计划员，而是增强计划员

现实工厂里，算法永远不可能一次性掌握全部现场信息。

因此，成熟 APS 系统的目标不是“生成后禁止人工改动”，而是：

```
算法先给出高质量基准解
        +
计划员在甘特图上继续修正
        +
系统尊重这些修正并支持重排
```

JVS-APS 当前系统的人机协同链路已经相当完整，尤其体现在：

- 生成排产
- 查看进度
- 预览结果
- 放弃或确认
- 甘特图调整
- 锁定后再重排

---

## 一、从“生成”到“确认”的计划生命周期

### 1.1 当前接口链路

`SmartSchedulingController` 已经把这条生命周期做成了独立 API：

| 接口 | 作用 |
|------|------|
| `/smart-scheduling/generate` | 生成排产计划 |
| `/smart-scheduling/plan/progress` | 获取排产进度 |
| `/smart-scheduling/plan/pending/cancel` | 放弃待确认计划 |
| `/smart-scheduling/plan/pending/confirm` | 确认排产计划 |

### 1.2 为什么“预览”和“确认”必须分开

因为排产结果是高影响决策：

- 直接决定现场派工顺序
- 会影响物料需求节奏
- 会影响设备资源占用

因此当前系统采用的不是“算完即生效”，而是：

```
求解结果
   ↓
待确认计划
   ↓
预览与人工检查
   ↓
确认生效
```

---

## 二、三类甘特图构成完整可视化闭环

### 2.1 当前系统支持的三种甘特图

后端 `ScheduleResultController` 和预览接口共同支持：

1. 资源甘特图
2. 订单甘特图
3. 物料需求甘特图

这三者分别回答不同问题：

| 甘特图 | 计划员真正关心的问题 |
|------|-------------------|
| 资源甘特图 | 设备是不是排满了，哪里冲突，哪里空档 |
| 订单甘特图 | 某张订单推进到了哪一步，是否会拖期 |
| 物料需求甘特图 | 未来几天哪些物料会被拉动，是否会断料 |

### 2.2 预览模式与正式结果模式

前端 `preview.vue` 把预览能力单独抽了出来，并通过 `disableHandle=true` 关闭交互操作。

这说明当前系统有意识地区分了两种使用语境：

- **预览模式**：先看结果，不动任务
- **正式模式**：进入资源甘特图后继续调整

---

## 三、资源甘特图为什么是前端核心工作台

### 3.1 当前资源甘特图已经不是“查看器”

`resourceGantt/index.vue` 暴露了大量操作入口：

- 撤销
- 拆分
- 合并
- 移动
- 锁定
- 解锁
- 报工
- 派工
- 参数设置

这意味着资源甘特图承担了真正的计划调度台角色。

### 3.2 当前交互设计的特点

从实现看，它至少具备以下工程特征：

- 使用 `@visactor/vtable-gantt`
- 支持 tooltip 与任务详情
- 支持任务选中
- 支持链接线管理
- 支持不同时间范围显示
- 支持预览与正式操作两种状态

换句话说，这不是“图表”，而是一个排产操作界面。

## 四、任务调整能力：当前系统已经具备的五种干预方式

### 4.1 拆分

`TaskAdjustController` 支持三种拆分：

| 接口 | 含义 |
|------|------|
| `/split/quantity` | 按拆出数量拆分 |
| `/split/evenly-task-number` | 按任务数量平均拆分 |
| `/split/completion` | 按完成数量拆分 |

这对部分完工、分批流转、分资源并行生产很有价值。

### 4.2 合并

`/merge/selected-tasks`

合并并不是简单 UI 操作，它代表计划员认为：

- 这些任务可以重新聚合为一个执行单元
- 当前排法过于碎片化

### 4.3 移动

系统支持：

- 移动指定任务位置
- 把部分完成任务进度移动到指定时间

这说明系统已经考虑到“任务并非总是从 0% 状态开始重新安排”。

### 4.4 锁定与解锁

支持两类锁定：

- 锁定指定任务
- 锁定已开工任务

这正好对应两个典型场景：

1. 计划员手工确认过的关键任务
2. 现场已经实际开工、不能再改的任务

### 4.5 撤销

当前系统还提供了“撤销任务调整”，但特别说明：

> 撤销移动、拆分、合并，不撤销锁定与解锁状态

这说明系统把“任务冻结状态”视为更高等级的业务决定。

---

## 五、为什么锁定机制是 APS 成败分水岭

如果没有锁定机制，排产系统会出现一个非常典型的问题：

```
计划员刚调好 3 个关键任务
      ↓
重新排产
      ↓
整个计划被算法重新洗牌
```

这会迅速摧毁用户信任。

JVS-APS 当前从三个层面处理了这个问题：

1. `ProductionTask` 中有 `@PlanningPin`
2. 资源时间推导时会避开锁定任务
3. 确认计划时会保留锁定调整、清空未锁定变更

这是一种非常典型、也非常实用的“人机协同优先级设计”。

## 六、本章总结

### 核心原则

1. **求解器先给出方案，但最终计划必须允许人工校正。**
2. **三类甘特图分别服务资源、订单和物料三个观察视角。**
3. **资源甘特图是当前系统最核心的计划工作台。**
4. **锁定机制决定了系统能否真正被计划员信任。**

### 关键数字

- 排产生命周期主接口：4 个
- 甘特图类型：3 类
- 任务调整能力：5 组（拆分、合并、移动、锁定、撤销）
- 拆分方式：3 种

第七章将站在更高层面，讨论 **JVS-APS 的生产落地、运行治理与演进路线**：包括当前系统已经具备的生产特征、落地时最容易踩的坑，以及后续可以继续增强的方向。
