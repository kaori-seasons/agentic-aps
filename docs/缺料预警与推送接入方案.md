# 缺料预警与推送接入方案

`docs/外部系统批量数据同步接入方案.md` 的姊妹篇。前一篇解决「数据怎么进来」，本篇解决「缺料怎么被看见、怎么被推走」。

版本：2026-11。适用范围：`aps` 后端、`aps/sql` 迁移脚本、接入端与通知渠道。

---

## 0 摘要

系统当前不预警。缺料不会触发任何通知，它被折算成开工日期往后推，然后就结束了。查了一遍代码，没有定时扫描告警、没有邮件、没有 webhook、没有 WebSocket、没有 SSE，主方案里设计的 `GET /shortage/{id}/impact` 与 `POST /shortage/{id}/notify` 都还在纸上。

更要紧的是，缺料的三类关键信息在求解器汇出边界上就被丢掉了：欠料图上只有物料 id 与缺量，延迟记录上只有物料 id 与时长，「哪些在途因为晚于交期被跳过」在扣减循环里直接 `continue` 掉了。外面看到的是日期变了，看不到缺什么、缺多少、为什么缺。

本方案的结论是两条预警线、一张欠料清单、四张支撑表、一份推送契约。

两条预警线不能合并。短周期齐套线按订单看，粒度到天，找采购催料；长周期水位线按周看，找采购走补货审批。两者对「缺料」的定义不同，混用会产生「排产说没问题、预警说缺料」的矛盾。

| 预警线 | 数据源 | 粒度 | 缺料定义 | 处理人 |
| --- | --- | --- | --- | --- |
| 短周期齐套 | `MrpUtils` 欠料图 + 在途扣减 | 订单、天 | 订单需求扣在库与可用在途后仍有缺口 | 采购、计划员 |
| 长周期水位 | `DemandPlanner` 时序库存 | 物料地点、周 | 场景水位低于安全库存或为负 | 采购、物控 |

四张支撑表：`jvs_shortage_item` 欠料清单、`jvs_shortage_alert` 预警台账、`jvs_shortage_rule` 预警规则、`jvs_shortage_notify` 推送记录。

推送契约复用接入方案的通用信封，`messageType` 取 `ALERT`。去重靠 `alertKey` 加时间桶，节流靠冷却期，等级升级除外。

需要先说清楚两件事：

第一，欠料清单不是新算一遍 MRP。它是把现有扣减过程的中间结果收集起来落库，算法不变。改造点在 `InventoryUtils` 与 `ProductionTaskUtils` 的返回值，不在 `MrpUtils` 的展开逻辑。

第二，本方案不解决安全库存与排产的关系。现状是排产扣减不考虑安全库存，安全水位只在需求预测模块使用。这个差异本方案如实标注（见第 7 节），不在这次悄悄统一掉。

## 1 缺料在系统里的真实行为

### 1.1 排产侧：缺料折算为开工推迟

`MrpUtils.calculateMaterialAvailability()` 从 BOM 顶层往下逐层展开，每一层做三件事：

1. `InventoryUtils.deductInventory()` 先扣在库，不够再扣在途；
2. 扣完仍有缺口的，作为欠料物料加进有向无环图（点是欠料物料，线是物料依赖关系）；
3. 把缺口乘以子件单耗，推下一层继续展开，直到没有欠料的层级。

在途扣减有一条关键规则，直接决定「缺不缺」的判定口径：

```
在途行的到货时间 + 物料缓冲期  >  订单交期  →  该行在途不参与分配，直接跳过
```

源码在 `InventoryUtils.deductInTransitInventory()`：`if (availableAt.isAfter(order.getDeliveryTime())) continue;`。恰好等于交期的来料仍可分配。

这意味着存在一种很隐蔽的缺料：**手上明明有在途，但因为到得太晚，系统当它不存在**。今天这种情况完全不可见——扣减循环里 `continue` 之后什么都没留下。

随后 `ProductionTaskUtils.getMaterialDelayMap()` 把每个欠料物料换算成延迟时长（提前期 + 缓冲期），挂到起始任务上，成为硬约束「物料最早可用时间」。最终落到 `ProductionTask.materialDelayMap`，类型是 `Map<String, Duration>`——**只有物料 id 到时长，缺量、到货时刻、跳过原因全丢了**。

### 1.2 需求侧：前瞻缺口已经是结构化的

`DemandPlanner` 输出 `Result.exceptions: List<Finding>`，`Finding` 是 `(reason, reference, at, quantity)`。缺料相关的 reason：

| reason | 含义 | `at` | `quantity` |
| --- | --- | --- | --- |
| `SHORTAGE` | 时序场景水位为负 | 发生周 | 缺口量 |
| `BELOW_SAFETY` | 低于安全库存但非负 | 发生周 | 距安全水位差额 |
| `STALE_ETA` | 在途承诺已过期仍有未清余量 | 原承诺时刻 | 未清余量 |
| `ORDER_LIMIT` | 采购建议被起订量或包装倍数卡住 | — | 差额 |
| `STORAGE_CAPACITY` | 采购建议被库容卡住 | — | 差额 |
| `PURCHASE_BUDGET` | 采购建议被预算卡住 | — | 差额 |
| `PURCHASE_PENDING_RECONCILIATION` | 尚有采购行待对账 | — | 0 |

配套的 `Point(at, flows, confirmed, scenario)` 给出每周的流水、已确认量与场景水位，通过 `GET /inventory-projections` 查询。

这一侧的信息是完整的，缺的只是推送——它现在完全是查询式，你不去查就没有。

### 1.3 现在丢在边界上的三样东西

| 丢失的信息 | 丢失位置 | 后果 |
| --- | --- | --- |
| 缺口数量、需求时刻 | `MrpMaterial` 只有 `id` + `quantity`，落图后不再回溯 | 看不到缺多少 |
| 被跳过的在途行及原因 | `deductInTransitInventory()` 直接 `continue` | 看不到「有货但到太晚」 |
| 预计到货、供应商、受影响下游任务 | `materialDelayMap` 只剩 `Duration` | 无法催料、无法评估影响面 |

本方案第 3 节的欠料清单就是把这三样接住。

## 2 两条预警线

### 2.1 为什么不能合并

两处对「缺料」的定义不一样，且都不该改：

| 维度 | 短周期齐套（排产） | 长周期水位（补货） |
| --- | --- | --- |
| 比较基准 | 订单实际需求 | 安全库存水位 |
| 是否扣安全库存 | 否，直接按订单需求扣在库 | 是，低于安全水位即告警 |
| 时间口径 | 订单交期、任务开工时刻 | 周 |
| 在途处理 | 只认到货时间 + 缓冲 ≤ 交期的行 | 认全部在途，按周归位 |
| 触发动作 | 催料、改期、分批 | 采购建议审批、补货 |

如果把两者合成一张预警表共用一套阈值，会出现两种误报：排产侧认为「这单齐了」而水位侧认为「该补货了」，或者反过来。这不是数据错误，是口径不同。预警台账必须带 `dimension` 字段区分，处理人和动作也要分开。

### 2.2 短周期齐套线

触发点在求解前后各一次：

- **求解前**：MRP 展开完成后立即生成欠料清单，不等求解结束。求解可能跑几十秒，缺料信息不必等。
- **求解后**：把欠料清单与实际排定的开工时间关联，得到「这次排产因为缺料推迟了哪几张单、推了几天」。

### 2.3 长周期水位线

触发点在补货运行完成后：`DemandPlanner` 的 `exceptions` 直接映射为预警，不需要二次计算。

## 3 欠料清单数据结构

### 3.1 汇总来源

欠料清单由三处现有计算的结果汇总，不新增计算：

| 字段来源 | 来自 | 现状 |
| --- | --- | --- |
| 缺口数量、需求物料、所属订单 | `MrpUtils` 欠料图节点 | 图上只有 id 与 quantity，需补记物料编码与订单 |
| 在库扣减量、在途扣减量、被跳过的在途行 | `InventoryUtils.deductInventory()` | 过程值未返回，需改为返回明细 |
| 延迟时长、最早可开工、受影响任务 | `ProductionTaskUtils.getMaterialDelayMap()` | 只返回 `Duration`，需补记时刻与任务 |

改造点集中在这三个工具类的返回结构，`MrpUtils` 的展开算法不动。

### 3.2 标准表 `SHORTAGE_ITEM`

对外标准格式，同时是 `jvs_shortage_item` 的落库结构。`dimension` 区分两条线。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `shortageKey` | string(160) | 是 | 幂等键，见下 |
| `dimension` | enum | 是 | `ORDER` 短周期齐套 / `WEEK` 长周期水位 |
| `source` | enum | 是 | `MRP` / `DEMAND` |
| `runId` | string(36) | 是 | 求解审计 ID 或补货运行 ID |
| `tenantId` | string(50) | 是 | 租户 |
| `detectedAt` | ISO-8601 | 是 | 发现时刻 |
| `dataCutoff` | ISO-8601 | 是 | 所依据的数据截止时间 |
| `severity` | enum | 是 | `P1` / `P2` / `P3` / `P4` |
| `reasonCode` | string(40) | 是 | 见第 4 节规则码 |
| `materialCode` | string(30) | 是 | 物料编码 |
| `materialName` | string(255) | 否 | 物料名称 |
| `unit` | string(20) | 是 | 计量单位 |
| `gapQuantity` | decimal string | 是 | 缺口数量，非负 |
| `requiredAt` | ISO-8601 | `dimension=ORDER` 必填 | 需求时刻，即订单交期 |
| `weekAt` | ISO-8601 | `dimension=WEEK` 必填 | 发生周的周一 |
| `orderCode` | string(255) | `dimension=ORDER` 必填 | 生产订单编码 |
| `locationCode` | string(96) | `dimension=WEEK` 必填 | 库存地点 |
| `onHandConsumed` | decimal string | 否 | 已扣在库量 |
| `inTransitConsumed` | decimal string | 否 | 已扣在途量 |
| `inTransitSkipped` | decimal string | 否 | 因晚于交期被跳过的在途量 |
| `skippedLines` | array | 否 | 被跳过的在途行明细，见下 |
| `availableInTransit` | array | 否 | 参与分配的在途行明细 |
| `earliestStart` | ISO-8601 | `dimension=ORDER` 必填 | 受影响任务最早可开工 |
| `delayDuration` | string(20) | 否 | 相对原计划的推迟时长 |
| `downstreamTasks` | array | 否 | 受影响任务编码 |
| `expectedEta` | ISO-8601 | 否 | 预计到货时刻 |
| `supplierCode` | string(96) | 否 | 供应商编码 |
| `safetyStock` | decimal string | `dimension=WEEK` 否 | 安全水位 |
| `scenarioBalance` | decimal string | `dimension=WEEK` 否 | 场景水位 |
| `status` | enum | 是 | `OPEN` / `ACKNOWLEDGED` / `RESOLVED` / `MUTED` |
| `resolvedBy` | string(96) | 否 | 处理人 |
| `resolvedAt` | ISO-8601 | 否 | 处理时刻 |
| `resolutionNote` | string(500) | 否 | 处理说明 |

`skippedLines` 与 `availableInTransit` 元素同构：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `lineCode` | string(96) | 在途行号 |
| `quantity` | decimal string | 该行数量 |
| `deliveryTime` | ISO-8601 | 预计到货 |
| `availableAt` | ISO-8601 | 到货加缓冲后的可用时刻 |
| `skipped` | boolean | 是否因晚于交期被跳过 |

**幂等键构造。** `dimension=ORDER` 时 `shortageKey = "{runId}:{orderCode}:{materialCode}"`，同一轮求解内同一订单同一物料只有一条；`dimension=WEEK` 时 `shortageKey = "{runId}:{locationCode}:{materialCode}:{weekAt}"`。同一 `runId` 重复落库幂等短路，不同 `runId` 视为新一轮，旧轮次的 `OPEN` 条目在新一轮落库时按同键覆盖而非新增，避免台账无限膨胀。

### 3.3 受影响任务与催料依据

`downstreamTasks` 元素：`{taskCode, orderCode, processCode, resourceCode, plannedStartTime, plannedEndTime}`。

`expectedEta` 的取值优先级：有可用在途时取该在途的 `availableAt`；有采购建议时取建议的 `availableAt`；都没有则为空——**空值必须显式呈现为「无到货计划」，不能省略**。省略会让计划员以为到货时间待定，实际上是根本没有在途。

## 4 预警规则表

### 4.1 等级

| 等级 | 名称 | 含义 | 默认响应时限 |
| --- | --- | --- | --- |
| `P1` | 红 | 已缺料且已影响上线，或订单已确定无法按期 | 30 分钟内响应 |
| `P2` | 橙 | 3 天内会缺，或在途承诺已失效 | 2 小时内响应 |
| `P3` | 黄 | 14 天内会缺，或低于安全水位 | 当班内响应 |
| `P4` | 蓝 | 数据质量提示，不直接是缺料 | 当日内响应 |

等级由规则决定，不由数据自己决定。同一份缺口在不同规则下可以是不同等级，取最高等级。

### 4.2 短周期齐套规则

| 规则码 | 条件 | 等级 | 默认阈值 | 接收角色 | 建议动作 |
| --- | --- | --- | --- | --- | --- |
| `MRP_GAP_FROZEN` | `gapQuantity > 0` 且 `requiredAt ≤ 冻结边界` | P1 | 冻结边界 = T+1 | 计划员、采购 | 立即催料或改期，准备分批 |
| `MRP_GAP_3D` | `gapQuantity > 0` 且 `requiredAt` 在 3 天内 | P2 | 3 天 | 采购 | 催料并确认到货 |
| `MRP_GAP_14D` | `gapQuantity > 0` 且 `requiredAt` 在 14 天内 | P3 | 14 天 | 采购 | 纳入催料清单 |
| `MRP_ETA_PASSED` | `inTransitSkipped > 0` | P2 | — | 采购、计划员 | 核实到货时间，或改交期，或分批 |
| `MRP_NO_SUPPLY` | 无在途且无采购建议 | P1 | — | 采购 | 立即下单 |
| `MRP_LEADTIME_VIOLATION` | 有在途但剩余提前期不足以按期到货 | P1 | — | 采购 | 加急或改期 |
| `MRP_RELEASE_BLOCKED` | 发布被齐套快照过期或 BOM 版本阻断 | P1 | — | 计划经理 | 重新同步后放行 |

`MRP_ETA_PASSED` 是本方案最要紧的一条。它对应 1.1 里那种「有货但到太晚」的隐形缺料，今天完全看不见。它的数据来自欠料清单的 `skippedLines`，不改造扣减逻辑就拿不到。

### 4.3 长周期水位规则

| 规则码 | 条件 | 等级 | 默认阈值 | 接收角色 | 建议动作 |
| --- | --- | --- | --- | --- | --- |
| `DEMAND_SHORTAGE` | `Finding` reason = `SHORTAGE` | P2 | — | 采购、物控 | 走补货审批 |
| `DEMAND_BELOW_SAFETY` | reason = `BELOW_SAFETY` | P3 | — | 物控 | 关注，不强制动作 |
| `DEMAND_STALE_ETA` | reason = `STALE_ETA` | P2 | — | 采购 | 核实交期或取消余量 |
| `DEMAND_PROPOSAL_BLOCKED` | reason ∈ `ORDER_LIMIT` / `STORAGE_CAPACITY` / `PURCHASE_BUDGET` | P3 | — | 采购 | 调整起订量、库容或预算 |
| `DEMAND_PENDING_RECONCILE` | reason = `PURCHASE_PENDING_RECONCILIATION` | P3 | 默认超 24 小时升 P2 | 物控 | 完成对账 |

### 4.4 数据质量规则

| 规则码 | 条件 | 等级 | 默认阈值 | 接收角色 |
| --- | --- | --- | --- | --- |
| `DATA_STALE` | 数据水位延迟超过该类允许窗口的一半 | P4 | 库存 15 分钟、在途 4 小时、订单实时 | 运维 |
| `DATA_SNAPSHOT_EXPIRED` | 齐套所依据的库存快照超过最大审批时效 | P4 | 24 小时 | 运维、计划员 |
| `SYNC_DEAD_LETTER` | 同步死信队列非空 | P4 | 超 30 分钟升 P2 | 运维 |
| `DATA_GAP_UNATTRIBUTABLE` | 欠料清单存在但 `orderCode` 为空 | P4 | — | 运维 |

`DATA_GAP_UNATTRIBUTABLE` 对应第 7 节要讲的归属问题：缺口来自多订单共享库存时，扣减顺序决定谁背缺口。这条规则用来兜住无法归属的残余缺口，不让它静默消失。

### 4.5 规则配置

规则不写死在代码里，落 `jvs_shortage_rule`，每租户可覆盖默认值。可配项：阈值（天数、小时数）、等级、是否启用、接收角色、通道、冷却期。

阈值必须按工厂实际节奏标定。三日、十四日、二十四小时这些默认值来自通用生产节奏，不是任何工厂的事实数据。

## 5 推送契约

### 5.1 通道

| 通道 | 用途 | 必选 |
| --- | --- | --- |
| 站内预警台账 | 所有预警落地，可查可处理可追溯 | 是 |
| 通用 webhook | 企微、钉钉、自建系统 | 建议 |
| 拉取出站 | 给 ERP、SRM 的结构化缺料清单 | 可选 |
| 邮件 | P1、P2 | 可选 |

站内台账是唯一必选通道，因为它是闭环的落点——预警必须有处理人、处理时刻和处理说明，否则告警只是噪声。

### 5.2 消息信封

复用接入方案 4.1 的通用信封，`messageType` 取 `ALERT`：

  "sourceInstance": "aps-prod-01",
  "tenantId": "plant-01",
  "alertKey": "MRP_GAP_FROZEN:ORDER:WO-2026-00417:M-10023:20261127",
  "alertId": "a5b4c6d8-7f9a-42a4-8f35-0a1b2c3d4e6f",

### 5.3 webhook 契约

| 项 | 约定 |
| --- | --- |
| 方法 | `POST`，`Content-Type: application/json` |
| 签名 | 请求头 `X-Aps-Signature: sha256={HMAC(secret, body)}`，接收端必须校验 |
| 超时 | 连接 3 秒，整次 10 秒 |
| 成功判定 | HTTP 2xx |
| 重试 | 失败退避重试 3 次（1 分钟、5 分钟、25 分钟），仍失败进 `jvs_shortage_notify` 的失败态并告警 |
| 幂等 | 接收端按 `alertId` 去重；同一 `alertId` 重复投递必须幂等 |
| 限流 | 单接收端每分钟最多 60 条，超出排队不丢 |

### 5.4 去重与节流

**去重键**是 `alertKey`，构造为 `{ruleCode}:{dimension}:{entityKey}:{bucket}`。`entityKey` 是 `orderCode:materialCode` 或 `locationCode:materialCode:weekAt`。`bucket` 是时间桶，按等级取粒度：

| 等级 | 时间桶粒度 | 含义 |
| --- | --- | --- |
| P1 | 小时 | 同一小时不重发 |
| P2 | 小时 | 同一小时不重发 |
| P3 | 天 | 同一天不重发 |
| P4 | 天 | 同一天不重发 |

**升级例外。** 等级升高时立即重发并生成新的 `alertId`，不受冷却期限制。例：`MRP_GAP_14D`（P3）升级为 `MRP_GAP_3D`（P2）必须立刻推，不能等到当天结束。

**静默期。** 同一 `alertKey` 在冷却期内再次触发只更新台账里的最新观测值与观测次数，不新建推送。台账要能看到「本条已观测 17 次」，否则会误以为只发生过一次。

### 5.5 回执与闭环

| 回执 | 含义 | 台账状态流转 |
| --- | --- | --- |
| `ACK` | 已接收，处理中 | `OPEN` → `ACKNOWLEDGED` |
| `RESOLVED` | 已解决 | 任意 → `RESOLVED`，记 `resolvedBy` / `resolvedAt` / `resolutionNote` |
| `MUTED` | 静默，本条不再推送 | 任意 → `MUTED`，需填理由 |

三种回执都必须落 `jvs_shortage_notify`，作为推送闭环证据。没有回执的预警不算送达。

`MUTED` 有边界：P1 不允许静默。P1 静默会把「已经上线受阻」压成噪声，这与产品定位里「宁可不给方案也不给破规矩的方案」是同一条原则。

### 5.6 端点

## 6 落地路线

### 6.1 一期：把缺料算出来并看得见

- 改造 `InventoryUtils.deductInventory()` 返回扣减明细：在库扣减量、在途扣减量、被跳过的在途行及原因。算法不变，只把过程值带出来。
- 改造 `ProductionTaskUtils.getMaterialDelayMap()` 返回结构化延迟：物料、延迟时长、最早可开工、受影响任务。
- 新建 `jvs_shortage_item`，MRP 完成后立即落库。
- 欠料清单查询接口上线。
- 顺带修一个隐患：`deductInStockInventory` 与 `deductInTransitInventory` 会就地改写 `material.setQuantity()` 与 `incomingMaterialOrder.setQuantity()`，`BasicData` 被多订单共享时库存是先到先得。改造时必须把扣减状态显式建模为独立的分配游标，不能继续写回共享模型对象。原因见 7.3。

验收：构造一张「有在途但到货晚于交期」的订单，欠料清单里 `inTransitSkipped` 大于零且 `skippedLines` 有明细；`gapQuantity` 与 MRP 图上的缺量一致；同一 `runId` 重复落库不产生第二条。

### 6.2 二期：预警台账与规则

- 新建 `jvs_shortage_rule`、`jvs_shortage_alert`，规则默认值内置，按租户可覆盖。
- 长周期线接 `DemandPlanner.exceptions`，直接映射为预警。
- 站内台账上线，含确认、解决、静默三个动作。
- 四条数据质量规则上线。

验收：一份缺料数据同时产生 `MRP_GAP_FROZEN` 与 `MRP_GAP_3D` 时只保留最高等级；同一天重复扫描不重复建台账；P1 静默被拒绝。

### 6.3 三期：推送

- 新建 `jvs_shortage_notify`，通用 webhook 通道上线，含签名、重试、退避。
- 拉取出站通道输出缺料清单给 ERP 与 SRM。
- 邮件通道按需。
- 回执闭环打通。

验收：webhook 接收端不可用时重试三次进失败态并告警；同一 `alertId` 重复投递被接收端幂等；等级升级时立即重发。

### 6.4 明确不在本期

- 短信、语音电话。
- 预警自动生成催料单或采购单。预警只提示，不代替人下单。
- 跨租户预警聚合。
- 用大模型生成预警文案或建议动作。`title` 与 `actionHint` 走模板，不做生成式文案。

## 7 自我辩证与反思

**7.1 两条线口径不同，统一台账仍然可能被误读。**

第 2 节坚持两条线分开，但它们最终落进同一张台账、同一个列表页。计划员打开列表看到 20 条，其中 8 条是水位线、12 条是齐套线，很容易混着看，得出「怎么这么多缺料」的错误结论。分开字段不够，界面必须默认按线分组，且水位线默认折叠。这条本方案没写进契约，属于实现层必须补的，不能只靠字段区分。

**7.2 `MRP_ETA_PASSED` 依赖的数据现在根本没有。**

这条规则是全篇最要紧的，也是唯一需要改动算法输出结构的。`deductInTransitInventory()` 里那个 `continue` 之后什么都没留，要拿到 `skippedLines` 就必须改返回值。改造本身不难，难的是要同时保持扣减结果完全不变——欠料数量、延迟时长、排产结果一个都不能变，否则一期内的所有既有回归都会失真。这个「只加观察不改行为」的约束必须写进验收：改造前后同一输入的 `gapQuantity` 与排产结果逐字节一致。

**7.3 库存扣减是就地写共享对象，缺口归属依赖订单处理顺序。**

`deductInStockInventory()` 里 `material.setQuantity(result.getDeductQuantity())`，`deductInTransitInventory()` 里 `incomingMaterialOrder.setQuantity(...)`，都是把共享的 `BasicData` 模型对象就地改写。多个订单排产时，先处理的订单拿走库存，后处理的订单报缺料。

这在「多订单竞争同一批库存」的场景下是有意为之——总得有人缺。但它带来两个问题：一是缺口归属随订单处理顺序变化，同一份数据换个顺序就换个人背缺口，预警的可信度会被质疑；二是 `BasicData` 被求解过程污染后无法重放，与产品承诺的「相同输入可复现结果」冲突。

本方案 6.1 提出把扣减状态显式建模为独立游标，但这是个真改动，不是加日志。估时应按「重构库存分配」而不是「加返回值」算。若工期紧，至少要先做到：同一 `BasicData` 在一次求解内只扣一次，且扣减前记录原始量，供欠料清单与回放使用。

**7.4 安全库存与排产的关系没有解决。**

排产扣减不看 `safetyStock`，只按订单需求扣；需求模块看 `safetyStock`。结果是：一个物料可以排产齐套，同时触发 `BELOW_SAFETY` 预警。这是对的——排产回答「这单能不能干」，预警回答「该不该补货」——但现场的人会当成矛盾。

诚实的处置是把它说清楚而不是统一掉。若强行让排产也扣安全库存，会把本来能排的订单排不下去，得不偿失。本方案在 2.1 明确了口径差异，但没给现场一个「看到两条冲突预警时怎么判断」的话术，实施培训时必须补。

**7.5 时间桶定不好，要么告警风暴要么漏报。**

5.4 的时间桶按等级取小时或天。P1 按小时意味着最坏情况一天推 24 条同内容预警，虽然台账里是同一条累计，推送侧仍可能被渠道限流。反过来若 P1 改按天，紧急情况第一天推完就沉默 23 小时。

更稳的做法是「首推即时 + 后续按变更推」：只在缺口数量变化超过阈值（建议 10%）或等级变化时重推，不按固定时间桶。本方案没采用这个，是因为它需要在台账里维护「上次推送时的缺口快照」，复杂度高一档。建议三期之后再评估。

**7.6 webhook 签名有了，但没有回执通道的认证设计。**

5.3 定了出向签名，`ackUrl` 却没定入向认证。如果渠道端回调 `ackUrl` 可以伪造确认，预警台账的状态就是不可信的。必须补：回执接口走服务账号或独立签名，且 `alertId` 必须是本系统签发、不可伪造。这条本方案漏了。

**7.7 单机部署下 `@Scheduled` 的可靠性没有保证。**

预警扫描靠定时任务。现状是单机 Docker Compose，`@Scheduled` 够用；一旦二期上求解 Worker 独立伸缩，多个节点会各跑一份定时任务，造成重复扫描与重复推送。需要分布式锁或把扫描收敛到单一节点。需求模块的 `DemandPlanningWorker` 用租约令牌解决了作业队列的这个问题，预警扫描应当复用同一套租约机制，而不是另写锁。

**7.8 预警闭环依赖人真的去处理。**

台账、等级、时限都设计好了，但如果没有人被指定处理 P1，这套东西就只是把「看不见」变成「看得见但没人管」。第 4 节给每条规则标了接收角色，但角色到人的映射在生产组织里是另一套东西（见接入方案 8.10）。在 RBAC 落地之前，接收角色只能是配置文件里的静态名单，这意味着人员变动时预警会发给错误的人。这是本期无法解决的，必须在验收清单里单列。

## 8 风险清单

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 扣减明细改造改变既有结果 | 排产回归全面失真 | 严格「只加观察不改行为」，改造前后逐字节比对 |
| 缺口归属依赖订单顺序 | 预警可信度被质疑 | 显式分配游标，台账记录归属依据 |
| 两条线口径混淆 | 误判缺料规模 | 界面按线默认分组，水位线折叠 |
| 时间桶导致告警风暴 | 渠道限流、预警被忽略 | 三期后评估按变更推送 |
| 回执可伪造 | 台账状态不可信 | 补回执认证，`alertId` 系统签发 |
| 多节点重复扫描 | 重复推送 | 复用租约机制收敛到单一执行者 |
| 静默被滥用 | P1 被压成噪声 | P1 禁止静默 |
| 预期到货为空被忽略 | 计划员误判为待定 | 空值显式呈现为「无到货计划」 |
| 阈值未按工厂标定 | 该报不报、不该报乱报 | 上线前按实际节奏标定，规则可配 |
| 接收角色映射过期 | 预警发给错误的人 | 验收单列，RBAC 落地前人工维护名单 |

1. `shortage_key` 去掉 runId，改为业务自然键。3.2 的键构造含 runId，又要求"旧轮次按同键覆盖"，两者矛盾；含 runId 每轮求解都新增一行。超长键收尾改用内容摘要。
2. 键长放宽：`shortage_key` 400、`alert_key` 500。草案的键构造拼出来就超过草案自己给的 160/200。
3. 时间列统一 `DATETIME(3)` 且由应用写入；推送记录增加 `lease_until`（草案只有令牌没有过期，崩溃后行会永久卡在发送中）；推送唯一键改为 `alertId:channel:sha256(target)`（草案 `(alert_id, channel)` 在一渠道多接收端时撞键）；欠料清单增加 `first_detected_at / observed_count / last_evaluated_at / on_hand_available / supply_mode / reference / source_reason` 等列；`severity` 允许为空（未命中规则不等于 P4）。

**语义修订**

4. 在途规则互斥：`MRP_ETA_PASSED`（部分晚到，P2）与 `MRP_LEADTIME_VIOLATION`（全部晚到，P1）按"这批货是否整体赶不上"二选一，不并存。
5. `MRP_NO_SUPPLY` 收紧为"现在下单也来不及或已进冻结期"才升 P1（提前期+缓冲期计入），避免每一处尚有余量的缺口都报 P1。
6. `DATA_STALE` 与 `SYNC_DEAD_LETTER` 默认关闭：同步通道未落地，扫描报告如实记"跳过：数据源不可用"。
7. 冷却与重发补充：已确认（ACKNOWLEDGED）的预警不按同等级重发；降级不另起新预警；升级仍立即重发并生成新 alertId，旧预警置 `SUPERSEDED`。
8. 预警进入终态（解决、静默、接续）时，未投出的推送一并取消——已解决的问题不再被推出去。
9. 欠料清单默认视图只含 OPEN 与 ACKNOWLEDGED；MUTED 是人工明确"不再打扰"的状态，需显式 `includeClosed=true` 才可见。
10. `DEDUCT` 三列补充 `supply_mode`：`NONE` 必须显式呈现"无到货计划"，`IN_TRANSIT_LATE` 呈现"有到货计划但晚于交期"，与 3.3 的空值口径一致且可机判。

**补漏**

11. 5.6 端点之外补两个等价入口（`GET /shortage/items/detail?shortageKey=`、`POST /shortage/items/handle`）：业务键含保留字符时无法进路径变量。
12. 7.6 自认漏掉的回执认证已补：渠道回调走 HMAC 签名（时间戳+方法+路径+正文摘要）+ 时间戳容差防重放，alertId 系统签发，签名失败与不存在同应答。

**实现澄清（正文口径不变）**

13. `GET /shortage/items/{shortageKey}/ack|resolve|mute` 同时接受动词与分词形式（`MUTE`/`MUTED` 等）。
14. 多节点安全（7.7）靠行级租约认领（投递）与唯一索引去重（台账）实现，未另加分布式锁；周期复评是等级随时间升级的唯一途径，随后台任务常开。
15. 实施中发现一个存量缺陷（与本次改造无关）：同一外购件在一单 BOM 里缺两处时 `getMaterialDelayMap` 抛 `Duplicate key` 使整次求解失败。按 7.2"只加观察不改行为"未顺手修，已有刻画测试固定，应独立修复。
