# 自适应排程 V2：热启动、构造复用与规模预算

## 目标与实际机制

V1 的每个候选都从未分配任务开始构造初解。较大问题中，候选预算容易耗尽在构造阶段，尚未进入局部搜索就结束。V2 保留 jDE 的参数变异、交叉和选择机制，加入本次求解内的最佳可行解热启动，并按任务规模分配冷启动预算。

外层优化四个搜索参数；内层优化资源分配与任务队列。业务权重、任务、工艺、日历、物料条件、停机窗口和冻结边界在本次求解中保持一致。V2 不自动读取历史计划，不跨租户共享方案，不修改约束来换取可行性。

这是带最佳解复用的迭代局部搜索与参数进化组合。后续候选使用的起点可能比父代更好，因此候选得分包含“起点改善”和“参数作用”两部分；不能把所有收益归因于差分进化，也不能将候选得分直接用作跨案例参数推荐的训练标签。

## 热启动流程

1. 求解开始时保存原问题快照和原策略配置。首个候选仍使用原策略冷启动。
2. 候选结束后独立重算完整评分，并检查初始化完成、任务分配完整、硬约束可行、冻结前缀及冻结基线不变。
3. 仅当候选严格优于当前最佳方案时更新最佳方案；启用热启动时序列化一次最佳快照。
4. 下一候选从最佳快照恢复独立对象图，覆盖为本次请求的原策略配置，再解码本候选参数。资源、任务、物料等可变对象不与其他候选共用。
5. 检查每个有效任务恰好出现一次、资源引用指向当前对象图、冻结任务位于资源队列的固定前缀。重新更新影子变量并完整评分，要求评分与种子一致且冻结基线仍保持。
6. 校验通过后只配置 Local Search 阶段，跳过 Construction Heuristic。若结构、评分或冻结校验失败，恢复原始快照冷启动，并记录回退原因；快照反序列化或求解基础设施异常仍失败关闭，不静默掩盖错误。
7. 全局最佳方案始终保留，不因后续候选无效或得分降低而丢失。最终仍进入已有预览、源版本校验和人工确认流程。

这里复用的是可行排程起点，不是 Solver 的内部禁忌表、晚期接受历史或增量评分缓存。切换搜索模板会重新建立内层求解器状态。

## 减少重复构造和内存占用

- 可行解出现后，正常后续候选不再从空队列构造初解。
- 最佳快照仅在严格改善时序列化，平分不重复序列化。
- 评分验证使用本次求解专属的 SolutionManager；候选仍使用独立 SolverFactory/Solver，避免跨候选搜索状态污染。
- 种群成员只保存参数、F/CR 与适应度分数，不再为每个成员保留一整份排程对象图。运行中主要保留原始输入、全局最佳解、当前候选和对应快照。
- 不缓存相同参数的最终得分：热启动起点或剩余预算不同，复用旧得分会产生错误比较。

## 规模预算规则

`budgetMode=FIXED` 保留原来每个候选的时间、评分次数上限；`SCALE_AWARE` 为默认。所有模式均受 `totalSeconds` 总墙钟预算控制。

有效任务是未被合并到其他任务中的任务。规模指标为：

```text
size = max(未冻结有效任务数, ceil(全部有效任务数 / 2))
```

冻结任务虽然不移动，仍参与约束评分，因此保留一半有效任务数作为成本下界。资源数另行记录，但不将“资源多一定更慢”作为未经验证的规则。

| 分档 | 规模指标 | 冷启动时间额度 | 冷启动评分次数额度 |
|---|---:|---|---|
| SMALL | ≤ 48 | max(单候选基准时间, 总预算的 25%) | 基准评分次数 |
| MEDIUM | 49～120 | max(单候选基准时间, 总预算的 40%) | 基准评分次数 × 3 |
| LARGE | > 120 | max(单候选基准时间, 总预算的 60%) | 基准评分次数 × 6 |

冷启动额度受总预算及实际剩余时间截断，评分次数上限为 1,000,000。尚无可行解时，后续候选继续冷启动，每次重新受剩余时间截断。规则不保证任意规模均能在默认 180 秒内找到可行解。

热启动的实际时间额度为：

```text
min(单候选基准时间, 剩余时间 / 剩余计划候选数, 剩余时间)
```

这样优先让剩余候选获得尝试机会。单候选评分上限保持 `trialScoreLimit`。若评分次数提前耗尽，可能剩余墙钟预算；完成所有配置代数后不会擅自追加候选。`FIXED` 模式不做剩余候选均分。

这些阈值是可解释的启发式分档，不是从制造企业现场数据训练得到的性能模型。SCALE_AWARE 会提高冷启动评分次数上限，因此与 FIXED 的比较不能宣传为相同总评分次数下的算法收益。验证、快照和审计开销计入整体墙钟流逝，但 Timefold 采用合作式终止，单次移动、完整评分和持久化结束可能带来尾部超时；不能作为硬实时承诺。

## 配置与回退

```json
{
  "solverEngine": "TIMEFOLD",
  "materialConstrained": true,
  "randomSeed": 17,
  "adaptive": {
    "enabled": true,
    "warmStartEnabled": true,
    "budgetMode": "SCALE_AWARE",
    "populationSize": 6,
    "generations": 2,
    "totalSeconds": 180,
    "trialSeconds": 15,
    "trialScoreLimit": 5000
  }
}
```

前端排产策略新增“复用本次最佳方案”和“组合预算分配”。已有配置缺少新字段时采用 `true` / `SCALE_AWARE`；显式 `false` 会保留。无需数据库迁移。

- 检查热启动影响：保留 `FIXED`，单独开关 `warmStartEnabled`。
- 回退到 V1 的候选启动与预算方式：`warmStartEnabled=false`、`budgetMode=FIXED`。
- 回退到普通 Timefold：`adaptive.enabled=false`。

开关回退不恢复已修复的安全检查，也不撤销已经确认的业务计划。

## 审计与诊断

`result_json.adaptive.algorithm` 为 `JDE_TIMEFOLD_V2`。顶层新增 `budget` 和 `warmStartEnabled`；每个候选新增 `execution`：

| 字段 | 说明 |
|---|---|
| `startMode` / `constructionEnabled` | 实际冷／热启动及是否启用构造阶段 |
| `seedTrial` / `seedScore` | 热启动来源候选及其分数，冷启动无来源时为 -1 / null |
| `fallbackReason` | 种子校验失败时为 `WARM_SEED_VALIDATION_FAILED`；此时保留尝试使用的来源信息 |
| `budgetMillis` / `scoreLimit` | 实际授予内层求解器的预算 |
| `preparationMillis` | 快照恢复、种子验证及求解器准备耗时 |
| `solveMillis` | 内层求解和取消监测退出耗时 |
| `validationMillis` | 结果评分及结构／冻结门禁耗时 |

V2 的 `elapsedMillis` 包括准备、求解、结果验证；不包含后续最佳快照序列化与审计写库。与 V1 的单候选耗时字段比较时要注意口径。性能对照以 HTTP 整体完成耗时为准。

若长期出现 `warmTrials=0`，先看首个候选是否可行；若出现热启动校验回退，核对种子评分与影子变量一致性，不能通过关闭门禁解决。如果大规模问题只完成初代，应增加总预算、减少代数或修正模型，不能宣称已完成进化搜索。

## 测试与复现

后端回归包含：真实求解下七次热启动与固定种子回放、冻结与缺件／停机保持、逆排热启动、热启动后的取消、冷启动回退配置、任务重复／错误资源引用／冻结前缀拒绝、预算分档与剩余时间截断。完整构建结果及 HTTP 证据见本轮验收目录。

```sh
# 先按 docs/e2e/adaptive/README.md 启动专用隔离服务并部署本轮 JAR。
# 禁止指向生产库；夹具会重置专用容器的 demo 租户排程数据。
python3 aps/scripts/e2e_adaptive_warm.py
python3 aps/scripts/e2e_adaptive.py --scales '' --output docs/e2e/adaptive-warm/acceptance
```

对照脚本依次测试同一问题的 FIXED 冷启动、FIXED 热启动和 SCALE_AWARE 热启动，校验剔除数据库生成标识后的业务输入指纹一致。所有正向结果独立验证任务完整性、设备资格、工序前置、设备互斥、日历生产工时、物料与冻结条件；不以截图代替约束校验。大规模测试可能需要数十分钟，不能同时对同一隔离库运行两个修改数据的测试脚本。

原 V1 证据保留在 `docs/e2e/adaptive`，本轮结果另存 `docs/e2e/adaptive-warm`。固定评分次数先终止时可以回放；墙钟先截断时搜索轨迹可能因机器负载改变。现场上线仍应使用客户脱敏数据及目标硬件进行多轮对照。
