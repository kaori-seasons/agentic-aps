# 需求预测和智能补货开发落地方案

**迭代评审稿 · 2026-11-20**　项目基线 `315ef6d`，分支 `codex/需求预测和智能补货`。本文定义待开发能力、接口与发布条件。首期以一个租户、一个已对账库存地点、一个产品族及其常用外购件为试点。

## 1. 业务决策与成功条件

计划员要回答三个问题：未来几个补货周期需要多少、哪一天会跌破保障水平、采购今天应向谁订多少才能赶上。预测按周讨论，供应按实际时间判断，采购确认后才产生确定供给。排程员继续使用已批准的订单和来料做有限产能排程。

| 决策对象 | 首期交付 | 验收人观察什么 |
|---|---|---|
| 有独立销量的备件、备库成品 | 订单历史、统计基线、人工覆盖、订单冲销 | 销售计划员能从一个预测桶追到原始订单及当时版本 |
| 配置型整车、通用组件 | 按车型族评估总量，已签订单走有效配置 BOM，剩余预测按已批准配比展开 | 工艺负责人能解释每条组件需求来自确定配置还是预计配置 |
| 外购件 | 按预计可用日投影库存，生成有缺口日期、建议数量和释放日期的采购建议 | 采购可看到沿用现有来料、催交和新增采购对缺口的不同影响 |
| 自制件、多个供货仓、昂贵专用件 | 自制缺口进入计划员待办；跨仓调拨先模拟；配置专件默认按单 | 计划员审批后才把确定生产需求交给现有 APS，专件不会因销量外推而误购 |

**上线依据。** 同一批历史截点上同时比较「现行人工补货／现行静态安全库存」「朴素预测＋相同补货策略」「候选预测＋候选策略」。前两者分别回答业务净收益和预测模型的增益。实施前由采购、计划、财务登记目标服务水平、库存资金上限、允许加急次数与例外审批人。预测精度提高而缺货或资金占用恶化时，维持原策略并调查交期、批量或评价口径。

## 4. 从销售事实到净预测

1. **先定义销量。** 首期以销售订单的需求日期与订购数量作为需求信号。发货量用于履约验证；缺货期间发货为零可能是受限供应。记录订购、取消、退货、发运的业务时间与系统获知时间，按源行及修订号去重。商业取消修订订单净量，退货单独统计，重新验收入库后才增加可用库存。停供、缺数、真实零销量、促销大单分别标记；缺数不能补零。每周与 ERP 对账订单行数、数量、撤单和未履约余量。
2. **粒度与时间。** 基本序列为租户、物料、地点、周；渠道或客户仅在样本足够且能稳定匹配时细分。每个租户固定时区、周起始日和单位换算版本。配置型产品优先预测可备库的产品族；专用属具按单，通用件用剩余族量乘有效配置比例与 BOM 单耗。互斥选项的比例和须为 1；冻结历史版本，缺映射或配比失效送人工复核。独立售后用量另列，组件对内领用仅作回测证据。
3. **模型候选。** 始终计算最近一期与移动平均基线；有完整年度周期时加入同季朴素法，有足够重复周期再评估季节模型。平稳品用单指数平滑，有趋势品用阻尼趋势，间歇品比较 Croston-SBA 与简单基线。SBA 分别平滑非零数量与非零间隔，以两者之比乘偏差校正项。连续长期为零的停产品关闭自动建议；新品允许同族类比或有期限的人工量。ADI＝有效桶数／非零桶数，CV²按非零需求计算；它们只筛选候选，最终按样本外表现取舍。
4. **回测与发布。** 按多个历史截点滚动训练，以采购保护期为评价跨度。每折仅使用当时已知的订单版本、配置、可用交期及调整；保留末段独立验收。统计 WAPE＝Σ|预测−实际|／Σ实际、Bias＝Σ(预测−实际)／Σ实际，按品类/地点汇总分子分母；全零组改报绝对误差、误补数量。分别保存模型基线和人工版本的误差。样本少或候选未稳定优于基线时发布基线，记录降级原因。模型、参数、训练窗口、回测截点和输入摘要随运行归档。
5. **人工调整。** 计划员可对叶级桶录入绝对替换值、有效期及原因；空值继承基线，零是明确的零。编辑基于版本号，批准后生效，过期恢复统计基线。首期汇总页只读，避免父子层同时录入。批准版本在每次运行中固定。
6. **订单冲销。** 每个已确认销售行按承诺需求桶匹配同地点同预测组，先冲本桶。首期跨桶窗口默认零，开启时按距离、先早后晚和稳定行 ID 分配；每次冲销量均受行余量和桶余量上限约束。期内已发货仍消耗对应预测份额，但只将未交订单余额投入后续供应计划。逾期未交订单移入近期确定需求，其已冲销关系随行保留。取消、改期、跨周、部分交付按新快照重放，存储 order_line→bucket 的分摊，允许逆查。

例：本周总预测 100，已确认订单 70，其中 20 已交。剩余预测 30，未来待供为 50＋30＝80。如果期初可用已反映那 20 件出库，投影再扣 20 会误报缺件。若销售订单与已排制造单绑定，制造单是覆盖该订单的供应，二者只在各自角色计量。

## 5. 从库存投影到补货建议

**按事件算，按天展示。** 使用单一截点的可用实物期初，隔离质检、冻结、报废；专属预留只分给绑定需求。若期初已扣预留，同时移除被该预留覆盖的需求数量。同一时刻按验收可用、再按需求优先级及稳定 ID 分配；只有日期没有时间时采用双方约定的保守班次。组件优先取已批准计划的投料时间；尚无工序时间时用带来源标记的计划开工估计。原排程的订单交期判定继续按现有规则运行。不同截止点导致的缺口差异在工作台展示。

```text
确定期末余额(t) = 前期余额 + 本时段确定可用供给 − 本时段到期需求
未收余量 = 确认采购量 − 已收数量 − 已取消余量
预计可用时刻 = 到货承诺时刻 + 接收缓冲（若已有验收可用时刻，直接使用）
场景余额(t) = 确定余额(t) + 到 t 已可用的本轮建议数量
```

负余额保留为积欠。收货时同时减少未收并按质检状态增加相应库存；到期未收须更新 ETA，失效 ETA 转异常。已批准等待 ERP 回执的行锁定并显示为在办，其补货意图抑制重复提案，确认供给口径只纳入已对账供应。生产计划、调拨单与采购单各有唯一来源行键。

**安全库存与批量。** 固定策略沿用安全库存；数据充分时以目标周期服务率 α 估计保护期需求的上分位数，安全库存取 max(0, 分位需求−同期均值)。保护期等于供货提前期加复审间隔，回放真实提前期和预测残差，保留二者可能的相关性。同一周期内按相同旺淡季采样；样本不足用人工安全库存或同族等级，披露样本量。周期无缺货率与数量满足率分别验收。稳定、成本可信的物料可用 EOQ＝√(2×年用量×每次订购固定成本／每件年持有成本)作候选批量；成本未知则采用已批准的批量规则。

**滚动求量。** 按采购日历枚举释放窗口，以最早可用时点 a 和下次常规补货可用前一刻 b 为本次覆盖范围。区间出现低于安全库存的场景余额时，净补量取区间内最大正差额 `max(目标安全库存(t)−场景余额(t),0)`。该余额已含区间需求，避免再次加入提前期平均用量。净补量为正才应用获批批量下限、MOQ 和包装倍数，向上取整；把结果作为模拟到货加入后续区间。若供应上限、库容、资金约束与 MOQ 冲突，显示不可行原因与人工方案。已早于 a 的缺口单列催交、改源或延期，普通采购不得消除过去的缺货。回溯建议下单日使用供应商工作日历，并区分下单日、预计到货日、验收可用日。

**可手算的采购样例。** 单位为件。周一起初 14，周一需求 6；一笔 PO 原订 10，其中 4 已收且包含在这 14 件中，余 6 在周二领料前可用。周二需求 12，周三需求 7。无补货的日末余额依次为 8、2、−5。安全库存 3，今天下单最早周三可用，常规覆盖至周三末，净补量 8；MOQ 10、包装 4，生成 12 件，周三模拟余额 7。周二的 1 件安全库存预警依旧存在。若剩余 6 件延期至周四，周二余额 −4 触发催交，周三净补量 14、建议 16。审批一条建议、ERP 回写一笔确认供应后重跑，同一数量只出现一次。

## 6. 存储、接口与并发契约

下表是建议的逻辑表，实施时沿用 MySQL、MyBatis-Plus 与现有迁移方式。所有业务唯一键均以非空 tenant_id 开头，物料关联使用稳定 ID，展示时再取编码；数量使用与 BOM 六位小数相容的 DECIMAL，包装舍入只在订单边界执行。时点存 UTC，业务日历与原始时区一同保存。跨地点明细不向仅按物料聚合的旧接口全量回灌。

| 数据组 | 最小字段与业务键 | 写入／读取约定 |
|---|---|---|
| demand_event / inventory_event | 源系统、源行、事件号、revision、地点、物料、数量、单位、类型、effective_at、known_at、引用行 | 源事件唯一；冲正追加反向记录。按租户、地点、物料、业务时间索引，同时保留摄取水位 |
| sourcing_rule / inventory_policy | 地点、物料、供应商、生效区间、日历、交期、缓冲、MOQ、倍数、策略、目标服务率、上下限、版本 | 同一主供应路径有效期无重叠；采购与计划分别维护。无有效来源、换算或接收日历时阻断释放 |
| planning_run / forecast_bucket / consumption | run_id、as_of、输入水位、策略／代码版本、序列桶起点、baseline、override、total、consumed、net、order_line、分摊量 | 成功运行原子切换可见版本；按运行、序列、桶唯一，分摊键另含订单行。运行失败时可继续读上次发布版，页面显示数据时效 |
| stock_projection / demand_link | run_id、时点、地点物料、源事件、毛需求、确定收货、余额、模拟余额、目标、销售／BOM／工单引用 | 保留首次缺口时刻和最晚释放日，支持从建议追到计算明细；快照内每个物理供应行只入一次 |
| supply_proposal / outbox / erp_receipt | 稳定建议 ID、业务意图键、输入版本、供应商、数量、释放日、可用日、状态、审批版本、外部行号 | ERP 外部行唯一，outbox 事件唯一；同一活动采购意图仅一条，跨运行按已批、在办和确定供给重新对账 |

**建议的 API 契约。** 下列是新增接口，统一挂在现有业务 API 前缀下。所有列表分页，异步调用返回 runId 或 proposalId；租户由登录上下文确定，后台任务显式恢复租户上下文。

| 方法和相对路径 | 请求要点 | 正常与冲突行为 |
|---|---|---|
| POST /demand-events:import | source、batchId、记录与源修订号 | 返回接收、重复、隔离计数及可下载错误行；重送同一批返回同一摘要 |
| POST /planning-runs | asOf、locationIds、horizon、scenario、Idempotency-Key | 202；同键不同载荷 409。作业按快照依次完成预测、冲销、投影、建议，按租户及发布范围串行切换 |
| GET /planning-runs/{id}；GET /forecasts；GET /inventory-projections | runId、地点、物料、起止桶 | 返回作业阶段、覆盖率、过期标记、预测量、余额构成及来源引用 |
| PUT /forecasts/{bucket}/override | 绝对值、原因、到期、expectedVersion | 计划员编辑，主管发布；版本落后 409，数量非法 422 |
| GET /supply-proposals；POST /supply-proposals/{id}/approve | 按缺口日排序；审批含数量、原因、版本、幂等键 | 审批事务内复查库存水位、价格／批量规则及原意图，过期要求重算。成功同时写 outbox |
| POST /supply-receipts | ERP 消息号、采购行、外部状态、修订、数量和 ETA | 验证发送端身份；重复回执幂等、乱序按修订处理。未知行隔离，禁止据此新建采购建议 |

**发布一致性。** 工作流从草稿进入待批，再到已批待发送、等待回执、ERP 已确认；另有驳回、作废和待人工核对。只有前两种未批状态可被新运行自动替换。两个审批人并发时按租户、建议版本和活动意图加条件更新，同一事务写唯一 outbox。网络超时由发送器使用同一个外部幂等键查询或重试；ERP 不支持幂等或查单时转人工核对，避免重复下单。入库、撤销和重新承诺各自保留来源单据。旧建议撤销不等于已发采购单撤销，后者走采购变更审批。

## 7. 用户作业与生产运行

- **周度需求评审。** 销售计划员核对数据水位，在同一图上看历史订单、基线、覆盖值和净预测。对异常大单、新品转移和停产留原因；主管发布后冻结该版本。采购可从任一建议反查所用预测。
- **每日补货。** 仓储对账昨日期末及在途，系统按地点计算第一缺口并归类「可以常规补」「需催交」「资料不足」。采购打开一条建议，查看确定和模拟两条库存曲线，检查到货窗口、释放日和包装取整；能改数量但要记录理由。审批权限与查看、修改政策权限分别控制。
- **班中变化。** ERP 改期、部分收货或销售撤单触发受影响物料及 BOM 依赖子图重算，短时间多事件合并水位。若影响已批准制造计划，向排程员出具物料、预计可用时刻及受影响工单，再由现有流程决定重排。建议供给不得进入确定排程输入。
- **可观测性。** 每次输出租户、水位延迟、异常行数、序列数、模型降级率、冲销守恒差、缺口数、过期建议数、作业耗时与 ERP 回执延迟。单条日志只含审计 ID，无客户姓名、价格明细和凭据。重复外部单号或守恒差非零立即暂停该范围写出；按 runId、规则版本和输入事件重放。全量夜批与增量采用相同计算逻辑，定期比较两者结果。

## 8. 实施拆分、依赖及退出条件

建议以六个交付包排期。工期须在抽取真实样本、确认 ERP 协议和测得数据量后估算，审批写出单独灰度。

| 包 | 主要负责人／依赖 | 可独立演示的交付与放行条件 |
|---|---|---|
| A 基线与数据合同 | 销售、仓储、ERP、后端 | 取一个产品族和一个已结账周期，签字确认销售日期、取消、预留、分批收货和计量单位。核对期初＋收−发＝期末，形成对账差异清单 |
| B 预测与回测 | 算法、后端；依赖 A | 历史重建、朴素基线、候选筛选、覆盖审批；可复算至少三个互不穿越的历史截点，新品／间歇／停产品单列 |
| C 冲销与物料需求 | 计划、工艺；依赖 A、B | 订单、剩余预测、配置 BOM、已覆盖需求逐行挂接；改期、撤单与共享子件守恒，对照现有 MRP 双引擎回归 |
| D 库存投影与建议 | 采购、后端；可在 B 开发时用冻结需求样本并行 | 供应日历、在途、目标、批量、缺口解释。重复运行同快照得到相同建议；不启用 ERP 写出 |
| E 工作台与 ERP | 前端、集成、测试；依赖 C、D | 从缺口审批到回执、部分收货、关闭；验证权限、超时、并发审批和死信恢复，生产试点前用 ERP 测试账套演练 |
| F 影子运行与扩围 | 业务负责人、运维 | 先只读并行，至少覆盖完整补货周期；延迟采购需跟踪至收货完成。逐地点开启建议、审批和 ERP 写出，达标再扩品类 |

**迁移与回退。** 先增表、索引与只读权限，按 tenant＋地点从 ERP 回填销售历史和一个有来源的余额截点；从相同水位重放增量。旧表余额缺地点时仅映射双方确认的一个地点；遇到多仓或空租户先隔离。旧来料和新 PO 使用同一来源映射，明确每个试点范围唯一库存读源与唯一回写方。数据对账通过后才启用新计算。通过分租户开关依次关闭 ERP 发送、审批、新版本发布即可回退；继续接纳已发单回执，逐条核对在途，保留审计与已发布历史。旧排产可独立运行。

## 9. 验收矩阵与反证

| 测试 | 固定输入／故障 | 判定标准 |
|---|---|---|
| 时间切片 | 晚录订单、跨周撤单、节假日、夏令时地点 | 历史截点只看当时已知记录；业务桶与当地日历一致；未来信息对历史预测影响为零 |
| 冲销 | 第 4 节例；跨窗口、跨客户／地点、订单超预测、重复导入 | 未交 50、净预测 30；桶冲销量不超过预测，行累计不超过可冲量，桶不为负；同一单重发无增量 |
| 配置与 BOM | 一族两种互斥门架，共用一套泵，另有售后 2 台泵；父件部分有库存、BOM 换版或成环 | 装配需求按净父件展开，两个选项合计等于族量；独立售后另加 2；在制覆盖与订单有唯一挂接；环或缺版本阻断发布 |
| 在途、批量与补货 | 第 5 节两种到货情形；5 件今天上午需要，下午才验收；MOQ 大于容量 | 建议分别为 12、16；上午短缺可见；冲突转例外。建议不改变历史余额，部分收货后现存＋未收对账 |
| 供应状态一致性 | 两人同时批准、已创建 PO 后响应丢失、回执乱序、重启、重复收货消息 | 同一意图 ERP 最多一张采购行，已发单可追踪；接收事件只生效一次，无跨租户可见数据 |
| 排产兼容 | 关闭迭代开关，同输入、固定测试设置，跑现有在途专项及双引擎正排／倒排 | 执行 `cd aps && mvn clean verify`；比较硬约束、任务完整性、冻结、前后置及欠料数量。启用预测、仅有建议时，确定供应与排程输入摘要一致 |
| 性能与恢复 | 试点实际峰值的两倍序列数、最长 BOM、并行 ERP 回调，夜批中途杀进程 | 在业务约定夜批窗口内完成；审批 P95、增量完成时限、恢复时限在 A 包签字。断点重启可重放，无半发布版本，跨租户越权测试全部拒绝 |
| 经营效果 | 同一供应延迟、期初、需求轨迹及预算比较三种策略，影子期后跟踪实绩 | 报告按时满足数量／到期需求量、缺货工单数、周期无缺货率、平均每日库存金额、加急次数与采购行数。按 SKU 价值和间歇性分组，列出改善及退化品 |

**如何推翻方案假设。** 若真实需求长期被缺货压制且客户只能提供出库量，模型会学习到供应上限；先改为基于确认订单的人工补货并优先补采失销／欠交数据。若交期波动主导缺货，锁定同一预测对比固定交期和实测交期分布，将资源转向供应商承诺质量。若准确率改善却出现更多零散 PO，固定需求比较不同复审周期与批量，以服务与总成本决定发布。若人工调整持续劣于基线，展示逐次调整的增益，收紧覆盖期限。若一个仓的改善来自抢占另一个仓的库存，暂停跨仓推广，先验证源仓服务和运输约束。

**评审结论。** 可先启动 A、B 和只读投影原型。首个业务验收点是采购能够从一条建议反查销售与物料来源、复算到货前的逐日余额，并在 ERP 确认与部分收货后得到一致结果。开放采购写出的条件是该链条通过异常演练、并行对账和业务签字。

## 10. 本分支的运行与验收

本分支已提供 Java 计算服务、MySQL 存储、Spring 接口、Vue 工作台和隔离账套验收脚本。入口是「生产计划 → 需求预测与补货」。首次使用先执行 [MySQL 8 迁移](../aps/sql/20261120_demand_planning.sql)，再启动现有后端和前端。版本号以地点、物料为范围，由数据源单调递增；每个快照只接收一个基本单位。

### 10.1 接口与输入约定

接口前缀为 `/mgr/jvs-aps/demand-planning`，使用已登录会话。查询与正常同步写入遵循现有 `R` 响应格式。接口调用方同时检查 HTTP 状态与业务 code。查询历史运行时绑定 tenant_id。查看自己的租户范围、提交覆盖、批准覆盖、批准采购和 ERP 回执使用独立权限。

| 操作 | 已实现的调用与边界 |
|---|---|
| 读老系统证据 | `GET /aps-inventory/{materialId}` 读取物料级现存、安全库存、进行中来料的源数量与加缓冲后的可用时间。租户范围、物料 ID 及物料编码映射到同一读事务。批量迁入前由仓储确认地点映射、数量语义和时区 |
| 导入对账数据 | `POST /demand-events:import` 或 `/snapshots`。每条销售行是带 knownAt、revision、due、ordered、shipped 的绝对状态。相同修订重送可复用，修订冲突整批回滚。后续版本可只传变化的销售行。库存、在途、配置、政策及采购日历每次传完整对账图像；消失的未结 PO 必须先传已收或已取消终态。接口以同一事务接收一条完整序列，错误反馈后更正并重送 |
| 查询及运行 | `GET /series?offset=0`；`GET /series/status?location=…&material=…`。以返回的 revision、generation 加 requestKey 提交 `POST /planning-runs`。传 `?async=true` 则返回 202，可通过 `GET /jobs/{id}` 查看状态；重试相同键可取得原运行。成功后 `GET /planning-runs/{id}` 返回完整结果，附 `/input` 可查看依据的快照 |
| 分页读取 | `GET /forecasts`、`/inventory-projections`、`/supply-proposals` 传 runId、offset、limit；默认每次 100 条，上限 500。余额明细包含销售、剩余预测、BOM 或采购行引用 |
| 覆盖审批 | 计划员通过 `POST /forecasts/drafts` 申请；主管通过 `POST /forecasts/drafts/{id}/approve` 批准。双人路径校验申请人与审批人、输入代次。主管亦可使用有单独权限的 `PUT /forecasts/override` 直接登记已批准调整。显式 0 代表零预测，null 恢复统计基线。旧运行保留当时的覆盖依据 |
| 采购与回执 | `POST /supply-proposals/approve` 传 runId、index、reason、可选 quantity。批准最早窗口后，ERP 使用 `GET /purchases?state=READY` 取待发单，以返回的 id 做外部幂等键。确认用 `POST /supply-receipts/{id}` 传 externalLine；明确拒绝用同一路径加 `/reject` 并传外部拒绝凭据编号及 reason。未知结果保持在办，先查询 ERP 状态。确认行在下一次库存快照按外部行号及确认数量对账。建议与 ERP 已确认但未入库存快照的单据分别展示 |

可从[HTTP 验收脚本](../aps/scripts/e2e_demand_planning.py)复制完整请求。以下为首笔导入示例，时间只是固定回放数据。现场审批需使用最新截点和仍可释放的采购日历窗口。

```json
{
  "location": "WH-A", "material": "PUMP-A", "unit": "EA", "revision": 1,
  "asOf": "2026-11-16T00:00:00Z", "zone": "Asia/Shanghai", "historyStart": "2026-11-16",
  "weeks": 1, "opening": "14",
  "policy": {"supplier":"S-A","purchased":true,"safety":"3","minimum":"10","multiple":"4",
             "maximumOrder":"60","nettingWeeks":0,"protectionWeeks":1},
  "sales": [
    {"line":"SO-1","revision":1,"knownAt":"2026-11-15T00:00:00Z","due":"2026-11-16T02:00:00Z","ordered":"6","shipped":"0"},
    {"line":"SO-2","revision":1,"knownAt":"2026-11-15T00:00:00Z","due":"2026-11-17T02:00:00Z","ordered":"12","shipped":"0"},
    {"line":"SO-3","revision":1,"knownAt":"2026-11-15T00:00:00Z","due":"2026-11-18T02:00:00Z","ordered":"7","shipped":"0"}
  ],
  "supplies":[{"line":"PO-1","ordered":"10","received":"4","cancelled":"0","availableAt":"2026-11-17T00:00:00Z"}],

```

期初 opening 是截点可自由分配的库存。已发运、专属预留和已验收数量须由同一 ERP 水位给出；预留对应的需求也要扣除已覆盖量。源单 ID 在地点、物料内唯一，接多个系统时应带系统前缀。历史起点表示从该周起全部销售记录均经过对账，历史缺失的序列应隔离或截短。资金、数量建议以十进制字符串传输，避免浏览器对长小数提前舍入。日期桶采用租户时区的周一零点；未指定日期的周净预测按该周起点需要处理，如截点已过则进入当前时刻。每个窗口的覆盖期终止于下个可用窗口，末窗口覆盖至预测范围末端。数据源需覆盖整个采购日历，否则末次建议可能偏大。

### 10.2 配置、批处理与运营

| 参数／数据 | 运行行为 |
|---|---|
| `aps.demand.jobs-enabled` / `auto-plan` | 均默认为 false。启用前先迁移数据库。启用 worker 后可请求异步作业，再启用 auto-plan 会在导入和覆盖发布事务中投递本序列重算。worker 使用数据库租约、SKIP LOCKED 和同一请求键恢复作业；输入已被替换则标记 SUPERSEDED；确定性输入错误进入 FAILED |
| `aps.demand.approval-tenants` | 逗号分隔的试点租户，默认空。发版可先影子计算。审批还需采购权限。默认每个物料地点同一时间只允许一个待对账采购意图；收回租户放行后，已发单仍可收回执 |
| `aps.demand.max-approval-age-hours` / `legacy-source-zone` | 默认分别为 24 和 Asia/Shanghai。库存水位过期或释放窗口已过均拒绝审批；老系统的无时区交期以配置的源时区解释 |
| 库存目标 | 固定 safety 可来自原物料主数据。可选 samples 传观测时刻、保护期 forecast/actual 与 serviceLevel；样本不足时返回固定目标及原因。可选 annualDemand、orderCost、annualHoldingCostPerUnit 三项生成 EOQ。maximumOrder、maximumOnHand 以及 purchaseBudget＋unitCost 可限制舍入后的采购单、地点物料库容及本序列可用预算 |
| 配置型产品 | 将族需求作为独立无库存序列计算。组件快照的 assembly 指向同租户同地点、同截点和范围的已发布 parentRun，提供 version、validFrom、validUntil、orderVariants、forecastMix、freeAssemblyStock、bom。已签行按确定配置，净预测按总和为 1 的配比展开，按时点优先消耗装配件可用库存。沿用同一 BOM 版本覆盖范围，换版处拆分或重做已批准图像；失效、缺映射、环路均阻断。组件独立售后销量使用本序列 sales。requirements 只导入尚未在该展开中体现的可追溯毛需求 |
| 供应承诺与 MRP | 建议只进入新模块的模拟余额。通过 ERP 现有的已确认采购／收货同步更新 MRP 的确定来料；本模块根据同一 ERP 来源行做对账。直接向旧来料表写草稿会让排程提前使用未承诺供给。多仓应先解决旧 MRP 单地点映射后再扩围 |
| 权限与运行审计 | APS_DEMAND_PLANNER 可申请覆盖并计算，APS_PLAN_MANAGER 可复核，APS_PURCHASER 可审采购，APS_DEMAND_CONNECTOR 可导入及收 ERP 回执。保留运行快照、算法版本、订单冲销明细、审批人及 ERP 行号。可按 job.state、purchase.state、available_at 跟踪作业失败、过期租约与超时回执；单个失败序列不覆盖上次成功运行 |
| 回退与容量 | 停止自动投递和审批，继续处理在途回执，按 runId 读取历史结果。运行采用单物料地点隔离，当前上限为历史 156 周、未来 52 周、单次销售修订 20,000 条、来料 5,000 条、JSON 快照 2 MB 量级。扩围前按真实峰值压测并评估分区、索引和归档周期 |

### 10.3 复现与现场放行

Java 17 下执行 `cd aps && mvn clean verify`，前端执行 `cd aps-ui && npm test && npm run build`。HTTP 验收需在一次性 MySQL 8 库加载 `aps/sql/jvs-aps.sql` 及本迭代迁移。启动后端时加载 `aps/scripts/e2e-local.yml`，覆盖数据源到隔离库，绑定回环地址，启用 `aps.demand.jobs-enabled=true` 与 `aps.demand.approval-tenants=demo`。运行 `python3 aps/scripts/e2e_demand_planning.py --base http://127.0.0.1:31820/mgr/jvs-aps --async-worker`。脚本使用独立物料编号，检查实际 HTTP、租户隔离、重复导入、并发采购审批、ERP 回执、预测双人复核及任务查询。

[经营效果回放脚本](../aps/scripts/evaluate_replenishment.py) 接受单地点物料的逐日连续轨迹。顶层字段为 opening、unitCost 和 days；每一天包含 day、demand、commonReceipts、realizedLeadDays，以及 current、naive、candidate 三套事先冻结的决策。每套决策提供 knownOn、release、可选 expedite。commonReceipts 只含对三种方案共同成立的期初在途；由模拟释放生成的到货须排除。程序以相同期初、真实需求和交期轨迹重算数量满足率、积欠、期末在途、平均日末库存金额与下单次数。无积欠天数是日指标，现场周期服务率应按实际复审周期另行汇总。

正式接入还需由实施方提供真实来源行映射、冻结销售历史、供应商工作日历及 ERP 幂等建单／查单契约。试点需覆盖至少一个完整补货周期，评审业务收益与退化物料，并完成双方认可的峰值容量与故障恢复验收。

### 10.4 本次实测记录

2026-11-20 使用 Java 17、MySQL 8.4 隔离库和实际 HTTP 会话验证。后端 clean verify 共 65 项通过，其中 12 项为新规划算法专项，其余覆盖已有排产等功能。前端 5 项既有测试通过，Vite 生产构建成功。浏览器实际登录后读取了预测量、冲销量、时序库存与采购审批表单。

- 固定验收样例重现 100 件预测、70 件订单、20 件已交对应的 80 件待供，按期部分来料与延期来料分别建议采购 12 件和 16 件。
- HTTP 验收中，同一采购建议的两个并发批准返回同一个 ID。ERP 确认后重复回执成功，更换已绑定的外部行号返回冲突；数量不符的快照整笔回滚，正确的部分收货回写后期末确定余额为 7。
- 不同租户读取历史运行返回 404；低权限账号不能计算或审批。计划员提交覆盖，主管批准后生成新代次，旧代次提交返回冲突。过期作业租约由 worker 接管，第二次执行成功，数据库结果为 DONE 且有对应 run_id。
- 本机单序列合成测试输入 10,000 条销售修订、104 周历史、26 周预测和 8 个训练截点。一次 HTTP 导入耗时 0.487 秒，同步计算含 HTTP 返回耗时 0.181 秒。此数值仅描述这次本机样本；租户总量、峰值并发、ERP 延迟和生产收益仍需现场实测。
