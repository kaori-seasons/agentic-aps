# CP-SAT 进程复用、局部优化与方案采用门槛

本轮在原有正排模型上增加运行时复用与稳定性控制，协议版本升级为 2。保留六项业务成本作为跨引擎对照口径，新增调整成本用于 CP-SAT 优化和方案采用。当前实现没有改变资源日历、订单级齐套、冻结与确认版本校验的既有语义。

## 1. 运行架构与 JVM 选择

OR-Tools 可以直接在主服务 JVM 内使用。本实现保留独立 Java worker，以隔离 protobuf/JNI 依赖、原生进程故障以及取消时的强制终止。进程复用解决重复加载成本，不意味着取消隔离。

- 同一服务实例最多两个 worker，计算线程总预算仍为八个；每个 worker 一次只处理一个请求，不允许同一 CpModel 并发求解。
- worker 按租户、jar 绝对路径、大小及修改时间绑定；更换租户或 jar 时不复用原进程。跨租户不共享模型缓存。
- 每个进程最多处理 20 次请求，空闲 60 秒由主服务回收；worker 自身有 120 秒空闲守护、父进程存活检查及每次求解截止时间。
- 应用正常关闭时终止所有 worker；取消、超时、异常退出、响应身份错误和模型运行错误会丢弃当前进程。下一次请求重新创建，旧请求不会自动重试或发布。
- 请求与响应保存在权限 `0700` 的临时目录，使用 UUID 文件名、原子响应落盘、协议版本与 attempt 校验。主服务限制 32MiB 请求、16MiB 响应。
- `reuseWorker=false` 可针对单次策略关闭进程复用，便于故障定位与冷启动对照。原有单次 worker CLI 仍保留。

这不是分布式任务队列：并发限制为单实例限制。多实例部署须由平台限制总 CPU、内存及进程数。`-Xmx512m` 只约束 Java 堆，JNI 内存仍需 cgroup/容器限额。生产发布必须同时更新主服务与 worker，不能混用 v1/v2 协议。使用不可变的版本化 jar 路径，禁止覆盖仍被运行中 JVM 使用的 jar；滚动部署通过新路径启动，再回收旧进程。

## 2. 精确模型缓存

worker 持有一个有大小上限的编译后 CpModel，最大序列化模型大小为 16MiB。大模型仍可求解，但不进入缓存；进程轮换和空闲回收限制长期驻留。

缓存键是语义请求的 SHA-256，包含：

- 时间原点、计划窗口、资源及停机/工作日历；
- 完整任务、设备资格、加工分段、释放时间、工序依赖、交期和冻结；
- 六项业务权重、完整基线、局部可调任务集合及调整成本权重。

只有 attempt、父进程 ID、随机种子、线程数和求解时间预算从缓存键中排除，它们不会改变模型可行域与目标。每次仍创建新的 CpSolver 并独立搜索；缓存不复用旧解、搜索状态或响应。

修改交期、到料、日历、权重、基线或局部范围会重新建模。仅改变随机种子、预算或发布采用门槛时可以复用模型。日历分段在主服务单次编译中按资源和加工时长复用；本轮没有引入跨请求主数据缓存。

审计新增进程 PID、是否复用、已完成请求数、进程启动耗时，以及 `performance.modelCacheHit/nativeLoadMillis/modelBuildMillis`。毫秒字段为整数，0 表示不足 1ms 或无需执行，不能解释为绝对零成本。

## 3. 局部优化

`optimizationScope=LOCAL` 必须有完整、可行且与当前模型一致的已确认基线，否则拒绝，不自动扩大为全量重排。

1. 使用 `focusTaskCodes` 指定种子任务。未指定时，选择逾期最严重的一个非冻结末工序；没有此类任务时，可调集合为空，保留基线。
2. 按 `neighborhoodDepth` 扩展双向工序依赖、基线中同设备的前后相邻任务。
3. 排除真实冻结任务，检查 `maxNeighborhoodTasks` 上限；超限明确拒绝，不静默截断。
4. 范围外任务的设备、开始和结束都固定。保留全部任务及跨范围依赖、设备占用、全局目标，保证边界约束完整。
5. 独立校验器再次确认范围外完全不变。

局部固定不等同于业务冻结：不会因此删除原有优先级惩罚等成本项。局部模式缩小的是搜索自由度，仍保留全量约束模型；它不是把整个工厂模型截成一个不完整的小图。返回 OPTIMAL 时，仅表示当前固定外部条件和局部范围内的最优，不代表全厂可调整时的最优。

当前局部模式用于有效计划的稳定改进；如果新停机/延期已使基线不可行，需要全量求解或后续专门的可行性修复流程。本轮不会把不可行基线当作安全回退方案。

## 4. 调整成本与目标

在六项业务成本 B 之外增加调整成本 D：

```text
D = 改变的任务数 × changedTaskWeight
  + 更换设备的任务数 × resourceChangeWeight
  + Σ ceil(|候选开工毫秒 − 基线开工毫秒| / 60000) × startShiftMinuteWeight

求解目标 = B + D
基线保护 = B + D <= B(基线)
```

“改变”指设备、开始或结束任一项不同；所有调整只相对于已验证基线计数。开工偏移按每项任务向上取整，1ms 变化计 1 分钟，防止用毫秒边界规避调整成本。结束时间变化计入任务改变，但不再额外计算结束偏移分钟，避免简单平移重复收费。

权重是评分单位，不默认代表人民币。默认每项调整 1000、每次换设备 3000、每分钟开工偏移 1；现场需根据交期与调整执行成本校准。

审计中的 `score` 和 worker `cost` 仍是六项 B，用于与原引擎比较；`performance.objectiveCost` 是 B+D，目标下界也属于 B+D。主服务独立重算两者，不使用浮点求解分数做发布判断。没有可行基线的首次计划 D=0。

## 5. 方案采用门槛

候选首先必须通过全局硬约束、原应用时间计算和目标一致性检查。随后按以下门槛决策：

- 任务完全不变：`UNCHANGED_BASELINE`，不创建重复待确认计划。
- 业务成本增加，或净收益 `B(基线)-B(候选)-D` 低于 `minNetImprovement`：`INSUFFICIENT_NET_BENEFIT`。
- 调整任务数占全部任务比例超过 `maxChangedTaskPercent`：`CHANGE_LIMIT_EXCEEDED`。
- 末工序总逾期整分钟改善少于 `minTardinessImprovementMinutes`：`TARDINESS_THRESHOLD_NOT_MET`。默认 0 表示不允许这一指标恶化。
- 全部通过：`ACCEPTED`，沿用原有待确认、预览与人工确认流程。

未采用时，审计保存原始候选及其指标、调整成本、净收益和原因，最终任务保持基线，候选模式下审计状态为 `BASELINE_RETAINED`，不写待确认表。页面隐藏确认/预览操作；直接调用确认接口也无法发布这次结果。首次可行计划为 `FIRST_FEASIBLE_PLAN`，不受相对基线的收益门槛限制。

默认最低净收益 1、最大调整比例 100%；因此默认保护调整成本，但未额外限制调整比例。建议稳定生产场景从 5%–10% 调整比例及业务认可的净收益门槛试运行，先用 SHADOW 观察拒绝原因。

## 6. 策略示例

在原有 `config.cpSat` 中设置：

```json
{
  "executionMode": "CANDIDATE",
  "numWorkers": 1,
  "horizonDays": 14,
  "useBaselineHint": true,
  "reuseWorker": true,
  "optimizationScope": "LOCAL",
  "focusTaskCodes": ["ORDER-001-TEST"],
  "neighborhoodDepth": 1,
  "maxNeighborhoodTasks": 60,
  "changedTaskWeight": 1000,
  "resourceChangeWeight": 3000,
  "startShiftMinuteWeight": 1,
  "minNetImprovement": 100,
  "minTardinessImprovementMinutes": 0,
  "maxChangedTaskPercent": 10
}
```

接口验证范围、重复/未知任务、负权重及整数溢出；局部模式关闭基线保护会被拒绝。候选模式仍要求启用开关、租户白名单以及三张任务表的 DATETIME(3) 迁移。本轮无需新增数据库字段，配置保存在原策略 JSON 中。

## 7. 验收与性能口径

[本轮真实接口结果、规模/种子对照及页面截图](e2e/cpsat-optimization/README.md)。

对照分为两个实验，不能混算提升比例：

1. 同一完整问题、相同种子，比较首次进程与复用进程，观察 JNI、建模、搜索与总耗时。
2. 24/48/72 道工序，每档 3 个种子，比较独立全量 CP-SAT 与自适应 Timefold。两者预算均为 30 秒、单线程、相同六项成本和约束数据；不传历史基线，因此调整成本为零。记录实际耗时、可行率、业务成本、逾期及缓存状态。

自适应 Timefold 使用原有热启动功能，种群 4、1 代、每次试探最多 10 秒、总预算 30 秒、每候选评分上限 1000000。达到总预算时可能未执行全部试探，报告保留实际次数。CP-SAT 达到 OPTIMAL 可提前结束；本轮运行中服务的 CP-SAT 可能命中缓存，报告明确标注，不能把热进程结果冒充每次都能获得的冷启动延迟。

另追加相同 9 组输入的 SCALE_AWARE 对照，共 27 次运行。72 工序中，SCALE_AWARE 将冷候选预算扩至至少 12 秒，并按剩余预算分配热候选，验证预算分配对可行率的影响。

再单独验证局部固定与采用门槛；局部受限解不能与允许全量调整的解直接宣称优劣。合成的单任务延期案例仅用于证明局部改进和发布闭环，不作为随机样本的平均收益。
