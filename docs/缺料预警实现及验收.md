## 2 与方案的差异（决策与理由）

### 2.1 键的修订

- `shortageKey` 不含 runId，改为业务自然键 `ORDER:{订单编码}:{物料编码}` / `WEEK:{地点}:{物料}:{规则码}:{引用}[:{周一}]`。方案键含 runId 又要求"旧轮次按同键覆盖"，两者矛盾；含 runId 每轮求解都新增一行，台账无限膨胀。超长键（订单编码最长 255 + 物料键 96 超列宽）收尾改用内容摘要，唯一性不受影响。
- `alertKey` 放宽到 500，推送唯一键改为 `alertId:channel:sha256(target)`。方案的 `(alertId, channel)` 在同一渠道配多个接收端时会撞键。
- 欠料清单增加 `first_detected_at`、`observed_count`、`last_evaluated_at`、`on_hand_available`、`supply_mode`、`reference`、`source_reason` 等列：待对账升级要从连续观测起点计时，冷却期内要能看见"已观测 17 次"，缺口归属要留档，"无到货计划"要显式可判。

### 2.2 语义的修订

- **在途规则拆成互斥两档**。方案 4.2 的 `MRP_ETA_PASSED`（部分晚到，P2）与 `MRP_LEADTIME_VIOLATION`（全部晚到，P1）在方案里并存但未说明互斥关系；实现里按"这批货是否整体赶不上"二选一。
- **`MRP_NO_SUPPLY` 收紧**。方案定为 P1，但"每一处尚有余量的缺口都报 P1"会淹没真正上线受阻的单子；实现收紧为"现在下单也来不及或已进冻结期"才升 P1，提前期+缓冲期计入判断。
- **`DATA_STALE` 与 `SYNC_DEAD_LETTER` 默认关闭**。它们依赖外部同步通道的批次表与死信表，该通道尚未落地（属姊妹方案一期）；默认关闭并在扫描报告里如实记"跳过：数据源不可用"，不按已支持口径给结论。
- **时间桶的升级例外收紧为"已确认不重发、降级不另起"**。已确认（ACKNOWLEDGED）的预警不再按同等级重发——有人在处理，每小时重复推同一条只会训练人忽略它；降级不另起新预警，旧的高等级预警留给人工处理。升级仍立即重发并生成新 alertId，旧预警置 SUPERSEDED。
- **默认列表不含 MUTED**。静默是人工明确"不再打扰"的状态，默认列表只看 OPEN 与 ACKNOWLEDGED；显式 `includeClosed=true` 才能看到静默与已解决。
- **终态即取消未投出的推送**。预警被解决、静默或接续时，队列里还没投出的推送一并取消——已经解决的问题不该再被推出去。这条方案没写，是端到端跑出来的。

### 2.3 回执认证（补方案的漏）

方案 7.6 自认漏了回执通道的认证。实现补上：渠道回调 ackUrl 没有登录会话，走 `ServiceRequestAuthenticator`——HMAC 签名覆盖时间戳、方法、路径与正文摘要，与出向推送共用接收端密钥；时间戳超出容差（默认 300 秒）拒绝重放；alertId 是系统签发的随机 UUID，签名失败与"预警不存在"返回同一句话，不给探测机会。

## 3 只加观察不改行为的验证

- 观察点全部走新增重载：`deductInventory` 与 `calculateMaterialAvailability` 的既有签名、算法、执行序一行未动；`deductInTransitInventory` 里被跳过的行只登记 `LineUse`，跳过行为本身不变。
- `InventoryObservationTest.observerDoesNotChangeTheShortageOrTheRemainingQuantities`：同一份输入（4 档库存 × 2 档缓冲 × 3 行在途）跑两遍，一遍带观察点一遍不带，断言缺料数量、在库余量、每行在途余量、预约时刻逐一相等——这是"逐字节一致"约束在扣减边界上的直接落实。
- `MaterialShortageCollectorTest.collectorDoesNotChangeTheMrpGraph`：带不带采集器，欠料图节点缺量与依赖形状一致。
- 全量回归：改动前基线 103 项，改动后 149 项全过，逐测试类数量与基线一致（存量无一变化），四模块 BUILD SUCCESS。

## 4 验收

**单元（149 项全过）**：观察点一致性 7 项；采集器 8 项（含一期验收三条件：`inTransitSkipped>0` 且 `skippedLines` 有明细、`gapQuantity` 与 MRP 图缺量一致、同键重复落库幂等由 e2e 覆盖）；规则引擎 15 项（窗口互斥、边界命中、租户覆盖、无等级不是 P4、待对账超时升级）；签名与回执 5 项（HMAC 契约、篡改拒绝、重放容差）；支撑 9 项（退避三档用尽、键与摘要、信封、十进制字符串与带偏移时间）；权限 7 项。

**端到端（14 用例全过，`docs/e2e/shortage/report.json`）**：真实 HTTP → APS → MySQL/Redis → Timefold → 本地 webhook 接收端，不打桩。复现路径：

```bash
JAVA_HOME=<jdk17> aps/scripts/start-shortage-e2e.zsh --disposable   # 需先建好 aps-ade-e2e 容器
python3 -I aps/scripts/e2e_shortage.py --base http://127.0.0.1:31820/mgr/jvs-aps
```

关键证据：部分晚到单 P2（在途扣 20、缺口 16、ETA=可用时刻），全部晚到单 P1（`IN_TRANSIT_LATE`、"有到货计划"、`delayDuration=PT120H` 即提前期+缓冲）；12 条预警一次签名送达；恒 500 接收端 4 次尝试后 DEAD 并生成只进台账的元预警；签名回执通过、错密钥/过期/伪造/陌生 alertId 一律 401；P1 静默 409、P2 静默需理由；新一轮求解未再观测到的条目自动关闭（静默的保持静默）且未投出推送取消；补货 Finding 直映射 WEEK 条目、下一轮未再报告即关闭；规则覆盖只改提交字段；出站拉取不改状态、回执才改；权限与租户隔离成立。

方案 6.1 验收逐条：有在途晚于交期的订单 → `inTransitSkipped=500`、`skippedLines` 有行号与可用时刻 ✓；`gapQuantity` 与 MRP 图缺量一致 ✓；同 runId 重复落库不产生第二条 ✓（`observedCount` 不变）。6.2：同数据多规则只保留最高 ✓；同日重复扫描不重复建台账 ✓；P1 静默被拒 ✓。6.3：接收端不可用重试三次进失败态并告警 ✓；等级升级立即重发——由单元测试与冷却语义覆盖，e2e 场景未跨时间桶，见第 6 节。

## 5 已知未解（本期明确不做）

- **库存扣减仍是就地写共享对象**。方案 7.3 的"显式分配游标"是重构库存分配，不是加观察，本期未做；已按"至少留档"落实：期初量、轮到本订单时的余量、扣减位次、排序规则全部落 `detail` 列，缺口归属可追溯、可解释。
- **存量缺陷：同一外购件在一单 BOM 里缺两处时任务生成抛 `Duplicate key`**，整次求解失败（`getMaterialDelayMap` 的 `Collectors.toMap` 无合并函数）。与本次改造无关（改造前即如此），按"只加观察不改行为"未顺手修；`MaterialShortageCollectorTest` 有刻画测试，欠料证据在异常前已采集落库。修复只需一行合并函数，应独立提交。
- **接收角色到人的映射**仍是配置文件静态名单（`aps.shortage.role-recipients`），RBAC 落地前人员变动会发错人——方案 7.8 的原话，验收单列。
- **时间桶按变更推送**（方案 7.5 的更稳做法）未实现，维持小时/天分桶。
- **邮件通道**需另配 `spring.mail.*` 与 `aps.shortage.mail.enabled=true` 才生效，端到端未实测 SMTP。
- **前端页面**未做；接口按方案 5.6 全量就绪，界面须按线分组并默认折叠水位线（方案 7.1）。
