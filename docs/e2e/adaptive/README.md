# 合成叉车装配：自适应排程 HTTP 验收

此目录保存 V1 历史证据，对应提交 `35fd14b`。当前代码已升级 V2；新版机制见[热启动与规模预算说明](../../自适应排程热启动与规模预算实现说明.md)，新结果见[本轮验收](../adaptive-warm/验收结果.md)。重跑新版脚本时请指定新的 `--output` 目录，保留这里的历史结果；复现 V1 应使用对应提交的代码和脚本。

本目录使用合成装配数据。E20/E30 为测试车型标签；工时、BOM 用量、设备能力均为软件验收参数。现场部署时按目标产线主数据、班组/工装资格、实际节拍和业务 SLA 配置与验收。

## 验收链路

生产构建前端 → HTTP 会话认证 → Spring Boot 可执行 JAR → MySQL 8.4 / Redis 7 → 实际 Timefold + jDE 候选搜索 → 持久化求解审计 → 候选预览 → 数据版本检查 → 确认入库。没有替换求解器或模拟 HTTP 返回。

数据覆盖两种成品、多层 BOM、车架切割/焊接/喷涂、液压预装、整车装配、性能测试，共 8 台候选设备。每张主订单展开 6 道工序，包含工作日、午休、夜间非工作时段、不同设备节拍和订单优先级。

夹具复用仓库演示 BOM 的结构和内部 ID/物料编码（例如 `FG-FAN-A/B`）；场景名称用于表达叉车装配流程，不等同于已导入真实叉车工程 BOM。正向规模样本与最终动态演示使用相同结构；最终演示的名称明确标注“合成”。

## 可复现执行

需要 Docker、Java 17、Maven、Node/npm、Python 3.9+。在仓库根目录执行：

```sh
# 专用容器名若已存在则退出，不会覆盖现有环境。
JAVA_HOME=/path/to/jdk17 MVN=/path/to/mvn zsh aps/scripts/start-adaptive-e2e.zsh --disposable

# 第二个终端：真实 HTTP 验收。仅连接 localhost:31010；仅改动专用容器。
python3 aps/scripts/e2e_adaptive.py

# 可选独立终端：在日志显示规模求解运行期间执行 8 并发 / 200 次已认证进度读取。
python3 aps/scripts/load-adaptive-e2e.py
python3 aps/scripts/load-adaptive-e2e.py --seconds 60

# 第三个终端：提供已构建的前端；沿用 Vite 配置代理到后端。
cd aps-ui
npm run preview -- --host 127.0.0.1 --port 9998
```

浏览器地址：`http://127.0.0.1:9998/jvs-aps-ui/index.html`。测试租户 `demo`，账号 `admin`，本机测试密码见 `aps/scripts/e2e-local.yml`。这些仅用于隔离环境。运行 JAR 使用独立临时副本，防止后续 Maven 构建覆盖运行包。

`--scales 6,12,24` 指定正向规模，`--scales ''` 只运行保护和动态流程；`--resume` 只复用同一计划日期的成功规模证据。脚本会重置专用容器中的 demo 排产数据，不连接现有业务数据库；不应改为业务容器或生产地址运行。

## 断言与证据

- 配置更新后经 HTTP 重新读取，断言服务真正支持并开启 adaptive，防止旧 JAR 静默忽略字段。
- 每个正向方案检查任务完整性、零硬约束违例、候选设备资格、工序前置关系、资源不重叠、班次起止边界、物料可用时间和冻结资源/起止时刻。另按日历独立累加生产秒数，核对数量与节拍；既有引擎按小时保留两位小数，允许最多 18 秒舍入差。
- 审计必须包含真实候选参数与得分；最终选中方案须是已完成可行候选中的最高分。
- 组合事件覆盖设备停机、关键件延迟、已导入订单提优插单、交期修改；四个预览接口返回数据后再确认。
- 检查匿名/低权限拒绝、租户审计隔离、并发只接纳一个求解、过期输入拒绝确认、取消后不重新发布、冻结任务与停机冲突时拒绝覆盖已确认计划。取消发生在实际候选完成且任务仍 RUNNING 之后；确认任务按编码、设备、开始和结束时刻逐项比对。
- 360 工序用刻意不足的单候选预算测试拒绝发布保护，不将该结果当作 360 工序可行性或性能通过。

`report.json` 是机器可读结论，`scale-*.json` / `baseline.json` / `dynamic.json` 是 HTTP 审计原文，内部包含原始快照和候选轨迹。`fixture-*.sql` 是本轮实际生成的可复用数据；`preview-*.json` 是实际预览接口响应。截图来自 BrowserOS neo 访问已构建的真实前端。

## 解释结果的边界

本轮独立校验发现并修复了两处日历问题：正排实际入口没有统一对齐班次，导致在班次结束时开工；周末被过滤成“无有效日历”，进而错误放开产能。现在所有正排起点先对齐工作时段，覆盖日期中的非工作日保持关闭；午休、周五班末跨周末、工作时长和逆排回归均覆盖。未配置日历时仍保留既有连续产能语义。

同时修复了可执行模块增量打包复用旧依赖的问题：`maven-jar-plugin.forceCreation=true`，验收另加配置读回断言，确保界面开关确实被运行中的后端接收。

预算失败用例还发现进度接口仅在成功后返回审计 ID。已将 ID 在持久化审计创建后立即写入进度，运行中、失败和取消均可通过带租户权限的审计接口追踪候选；不再依赖直接查询数据库取得 ID。

动态重排的真实任务预览还暴露了深拷贝对象身份问题：已有补充订单 ID 在基础数据中完成复用，但候选任务中的独立订单副本仍使用临时 ID。持久化前现在按订单编码将所有任务副本映射到规范 ID；不存在的关联会拒绝保存。回归覆盖多个独立副本与未知订单，HTTP 复测覆盖四种预览和实际确认。

此测试是单机、单次、顺序执行的规模与事务验收，另含 8 并发 / 200 次进度请求的短脉冲负载，以及 60 秒、8 会话、每会话请求后间隔 100 ms 的限速查询；不是多租户长期压力测试。样本 P95 不代表生产 P95、最大持续吞吐或 SLA。不同规模使用不同候选预算；不能将耗时差异直接宣传成算法加速比例。相同评分权重用于一个问题内部选优，跨规模的绝对 soft 分数不能直接比较。

生产上线前，使用目标产线的实际资源、日历与物料批次开展历史订单回放，并在目标硬件上确定规模分档预算与回退规则。软件验收结果与现场运行指标分别记录。
