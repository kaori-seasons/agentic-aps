# CP-SAT 模型裁剪与共享预算组合精修验收

本轮使用隔离合成数据和真实 HTTP 服务。业务输入为 24 / 48 / 72 道工序、8 台资源；每组使用随机种子 17、29、43，统一 30 秒总求解预算。完整输入、输出和审计保存在同目录 JSON 文件，聚合结果为 `matrix.json`。

## 主对照结果

27 / 27 次运行获得可行方案；每个规模每种算法均包含三个种子。下表为中位数，成本越小越好。

| 工序数 | 求解方式 | 加权成本 | 逾期分钟 | HTTP 秒 | 主 JVM + worker CPU 秒 |
|---|---|---:|---:|---:|---:|
| 24 | 自适应 Timefold | 1,796,962,708 | 0 | 30.329 | 32.460 |
| 24 | 独立 CP-SAT | 1,796,960,479 | 0 | 8.724 | 8.983 |
| 24 | 共享预算组合 | 1,796,962,228 | 0 | 30.319 | 31.406 |
| 48 | 自适应 Timefold | 1,800,444,562 | 4,962 | 30.337 | 31.980 |
| 48 | 独立 CP-SAT | 1,800,450,206 | 9,822 | 30.361 | 30.630 |
| 48 | 共享预算组合 | 1,800,437,149 | 9,534 | 30.414 | 31.322 |
| 72 | 自适应 Timefold | 1,806,727,583 | 20,368 | 30.233 | 32.580 |
| 72 | 独立 CP-SAT | 1,806,926,165 | 41,732 | 30.379 | 30.299 |
| 72 | 共享预算组合 | 1,806,718,142 | 23,778 | 30.268 | 31.775 |

**解释**：组合方案在 9 对同输入、同预算的比较中，加权总成本全部优于自适应 Timefold；其中 24 工序成本均减少 480，48 工序减少 6,042–8,223，72 工序减少 4,741–21,289。独立 CP-SAT 在 24 工序下仍获得更低成本，不能据此把所有场景都切换为组合模式。

**交期取舍**：组合方案在 48 工序的三组样本中逾期分钟均增加；72 工序有一组下降、两组增加。因此本轮证明的是配置权重下的总成本改善，不是交付全面改善。组合功能默认关闭；正式重排继续受逾期改善门槛约束，初排需先确认交期、负载、完工时间等权重符合业务取舍。

| 48 | 1,800,442,632–1,800,444,934 | 1,800,443,515–1,800,462,319 | 1,800,434,409–1,800,438,520 |

## 验证口径

- Timefold：自适应调参，`SCALE_AWARE` 预算。
- CP-SAT：全量独立求解，默认单线程、AUTOMATIC 搜索。
- HYBRID：Timefold 种子 + 渐进扩大瓶颈邻域的 CP-SAT 精修，共享 30 秒。不是两阶段各 30 秒。
- PORTFOLIO / TWO_WORKERS：分别改变 CP-SAT 搜索分支策略和线程数，其余业务规则、目标和预算保持一致。

每对样本核验业务输入指纹，HTTP 返回结果逐项验证任务完整、依赖、日历和资源可执行性。组合求解各轮范围单调扩大，最终加权目标不劣于任一已返回的候选；已有正式计划仍经过调整成本和采用门槛。

加权总成本不是单独的交付指标。不同目标存在取舍，必须同时查看逾期分钟和完工时间。局部求解的 OPTIMAL 只对审计中的可调范围成立。

## 搜索方式与线程对照

补充 6 次运行，三个规模均使用 seed=17。该组用于参数探索，未以单个种子决定全局最优参数。双线程保持相同墙钟预算，但不代表相同 CPU 预算。

| 工序数 | 配置 | 加权成本 | 逾期分钟 | HTTP 秒 | 主 JVM + worker CPU 秒 |
|---|---|---:|---:|---:|---:|
| 24 | PORTFOLIO | 1,796,962,187 | 0 | 30.294 | 30.621 |
| 24 | TWO_WORKERS | 1,796,960,479 | 0 | 4.075 | 7.440 |
| 48 | PORTFOLIO | 1,800,477,409 | 15,220 | 30.723 | 9.417 |
| 48 | TWO_WORKERS | 1,800,429,573 | 6,628 | 30.281 | 59.901 |
| 72 | PORTFOLIO | 1,807,571,616 | 93,994 | 30.546 | 30.737 |
| 72 | TWO_WORKERS | 1,806,818,688 | 43,116 | 30.329 | 59.575 |

双线程在本组 48/72 工序上改善了独立 CP-SAT 的加权成本，但 CPU 消耗增加。PORTFOLIO 在本组没有显示优势，默认保持 AUTOMATIC + 单线程。是否增加线程需结合设备配额、并发排程数量和更大样本复测。

## 模型规模实测

以下取各规模 seed=17 的全量 CP-SAT 输入；业务配置的换型成本与准备间隔均为零，因此设备互斥保留、circuit 省略。

| 工序数 | 变量数 | 约束数 | circuit 数 | 原日历分段 | 保留分段 |
|---|---:|---:|---:|---:|---:|
| 24 | 1837 | 4967 | 0 | 1648 | 1539 |
| 48 | 3916 | 10304 | 0 | 3296 | 3082 |
| 72 | 6232 | 15968 | 0 | 4944 | 4606 |

72 工序组合求解首轮仅移动 4 项任务，日历分段由 4,944 降至 215；随后扩展至 10、20、31 项，最后一轮保留 1,624 段。扩大范围始终受共享预算和 60 项任务上限约束。

变量变少不必然使所有实例更快：精确求解器的传播强度与搜索路径也会变化。因此没有根据单次结果提高默认线程数或自动启用组合模式。

## 性能口径

HTTP 时间包含数据库读取、轮询和序列化。父进程允许总求解预算之外 1 秒协议收尾；worker 原生库冷启动也占用总预算。冷启动样本保留在数据中，不为了好看的统计剔除。

主 JVM CPU 由测试脚本读取进程累计 CPU 差值，包含求解、GC 和同期服务线程；worker CPU 从其内部计量多轮加载/建模/搜索后累加。二者相加用于观察应用计算开销，不包含 MySQL/Redis CPU。`workerCpuComplete=false` 表示超时强杀导致最后一轮 CPU 未完整采到，不得当作完整总 CPU。

## 正确性与保护验收

- 后端回归：协议 1 项、worker 9 项、业务模块 103 项；覆盖相同最优成本、合法解枚举、冻结/日历/依赖、物料与原有需求计划业务。
- 前端：5 项测试通过，Vite 生产构建通过；保留现有较大资源包的构建提示。
- 33 次 HTTP 性能对照全部可行，业务输入指纹一致；九组组合结果均验证了范围单调扩大和保留最好方案。
- 四项真实 HTTP 保护验收通过，记录见 `acceptance.json`：首次种子进入待确认并正常确认；正式基线跳过重复种子且采用门槛生效；1 秒冷 worker 预算耗尽返回 `UNKNOWN / SHARED_BUDGET_EXHAUSTED` 并保留已验证正式基线；种子阶段取消后无待发布计划。

## 复现

先部署协议 v3 的主服务与 worker，连接专用 `aps_e2e` MySQL 和 Redis。脚本会重置隔离库 demo 排程数据。

```bash
python3 aps/scripts/e2e_cpsat_search.py --disposable --backend-pid <隔离后端PID>
python3 aps/scripts/e2e_cpsat_search.py --disposable --resume --orders 4 8 12 --seeds 17 --modes PORTFOLIO TWO_WORKERS --backend-pid <隔离后端PID>
python3 aps/scripts/e2e_cpsat_search.py --disposable --acceptance-only
```

实现、配置与边界见 [模型裁剪与组合优化手册](../../CP-SAT模型裁剪与共享预算组合优化.md)。
