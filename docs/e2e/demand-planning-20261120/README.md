# 需求预测与智能补货端到端验收

2026-11-20，在 `codex/需求预测和智能补货` 当前工作区重新构建并测试。浏览器使用 Vite 生产静态包，后端使用 Spring Boot 发布 JAR，数据库为全新 MySQL 8.4.13。登录、权限、后台计算、事务与数据库为实际实现。测试使用本机同源静态代理和隔离租户，ERP 侧由测试客户端按接口合同发送确认和收货数据。测试环境未连接客户 ERP。

**验收结果。** 浏览器对同一物料走完从预测、审批到到货对账的流程。来料延期使建议采购量从 12 件增至 16 件；重复确认后数据库仍只有一条 16 件的已对账采购记录。发现一处台账刷新显示问题，已修复并用重新构建的页面复验。

## 同一物料的三个版本

地点为总装一库，物料为液压泵 HP-25，基本单位为件。历史 16 周每周销量均为 25，本周三张订单分别需要 6、12、7。期初可用 14 已含原采购单已收的 4 件，该单未收为 6。安全库存为 3，MOQ 为 10，包装倍数为 4。下表余额为计划范围内的确定库存投影。截图时间列为 UTC。

| 输入版本 | 在本次采购可覆盖的区间中如何计算 | 实测 |
|---|---|---|
| 1，原在途按期可用 | 预计最低余额 −5，补到安全库存需 8，起订量和包装取整后为 12 | 页面、运行 API 同为 12 |
| 2，原在途延至最后一笔需求之后 | 预计最低余额 −11，净缺口 14，包装取整后为 16；新采购最早可用前已有 4 件短缺 | 页面、API 同为 16。采购员在浏览器填写原因并批准，数据库审批人为 buyer |
| 3，新增采购 16 已收 4 | 期初由 14 变为 18，新采购只计未收 12。期末确定余额为 18＋12＋原在途 6−总需求 25＝11 | 确定余额与场景余额均为 11，无新增建议。ERP 外部行 PO-QA-4316 对应唯一已对账采购 |

## 本轮修复与复验

在采购回执台账选中“已对账”后点击页头“刷新”，原页面先清空台账，但只重新读取计划，展开区域呈空表。已让页面在刷新或切换序列时按展开状态重新加载台账。相同操作在修复后的生产静态包中保留了对应的采购记录，见截图 08。

[结构化数据与构建摘要](evidence.json)包含三个版本的实际运行 ID、库存投影、采购记录及截图校验信息。[可重复执行的 HTTP 验收脚本](../../../aps/scripts/e2e_demand_planning.py)可在按[运行手册](../../需求预测和智能补货开发落地方案.md)配置的隔离库执行。本轮结果覆盖单地点试点流程；客户网关、真实 ERP 连接、现场主数据与峰值吞吐仍需上线前联验。
