# OR-Tools CP-SAT 实现与运行手册

## 目标与验收口径

本次实现将 CP-SAT 接入现有排程、预览、确认及审计链路。首要验收目标是正确性：任务完整、设备匹配、日历有效、工序关系成立、冻结不变、已预约物料到料后才能开工。逾期、等待、切换和求解速度的改善通过实验衡量，不由引擎名称推断。

“不劣于基线”仅在同一次问题快照、同一评分口径下成立：完整基线通过全部新模型约束后，作为提示并添加 `objective <= baselineCost`。返回结果再次独立校验；预算内无新解但返回 UNKNOWN 时，可以保留已经验证的基线。缺失、冲突或过期基线不会被当作可行方案。该保护针对配置的加权总成本，**不代表每个分项指标都不下降**。调整任务数目前是审计指标，不是第七项优化目标。

## 结构与依赖隔离

```text
租户鉴权 / 排产策略 / 原始输入签名
  → 既有 MRP 数量分配 + 实际在途预约时间
  → 冻结 / 动态事件 / 规划问题快照
  → CpSatProblemMapper（能力门禁、日历编译、完整基线验证）
  → 私有目录 JSON → 独立 Java worker → OR-Tools 9.15.6755
  → Protocol.verify + 应用时间复核
  → 影子审计 或 待确认计划
  → 原始输入签名复核 → 人工确认入库
```

- `jvs-aps-scheduling-contract`：不依赖 Spring、Timefold、OR-Tools 的协议、日历分段及校验器。
- `jvs-aps-ortools-worker`：固定 OR-Tools 9.15.6755、protobuf 4.33.1，独立可执行 jar；主服务不加载 JNI。
- `solve/cpsat`：主服务转换器及子进程监管。请求有协议版本、attempt ID、父进程 ID；响应必须匹配版本和 attempt。
- 原有 OptaPlanner、Timefold、自适应组合路由保留。CP-SAT 不接受 Timefold 的禁忌搜索、评分次数预算或自适应参数组合。

## 硬约束与日历

| 规则 | 实现 |
| --- | --- |
| 每个活动工序恰选一台合法设备 | ExactlyOne + optional interval |
| 设备互斥 | NoOverlap，整个开工至完工区间占有设备 |
| 跨午休、跨工作日加工 | 累计工作时间的分段仿射逆映射，毫秒整数精度 |
| ES / EE | 按现有 SchedulingRules 转换开始/完成约束、前后间隔和缓冲 |
| 最早开工 | 计划时间、前间隔、notBefore、已预约来料可用时间 |
| 停机 | 固定区间，先合并重叠停机窗，禁止与任务包络相交 |
| 冻结 | 资源、开始、结束三项固定；发生冲突时返回不可行 |
| 相邻工序准备间隔 | 资源 circuit 的相邻弧约束 |
| 完整性 | 独立核验任务标识集合、重复、遗漏、资源和依赖 |

日历休息不是设备 NoOverlap 中的固定障碍：当前系统允许工序跨休息继续加工，并在整个包络内占用设备。模型严格保留这一语义。资源未配置日历、或时点未被任何日历覆盖时，沿用系统已有的连续可用语义。

日历分段不会向秒或分钟取整。对于跨午夜未拆分班次、亚毫秒输入、未规范化的合并子任务依赖、超过任务/分段/排序规模门槛的输入，明确拒绝，不静默降精度或删除规则。最终还会用应用 `ProductionTask.getEndTime()` 复核结束时间，避免编译器与既有日历实现的边界差异进入待确认计划。

## 物料数量与时间

MRP 继续按已有规则扣减在库和在途数量，不重复使用已分配数量。新增回调保留实际被扣减的来料批次可用时间（预计到货 + 物料缓冲）。对同一主订单取最后可用时间，作为其工序的保守齐套放行时间，随后与动态 `notBefore` 取较晚值。

这个实现有意采用**订单级齐套**：能够阻止到料之前开工，但可能延后本可先行加工的独立支路。它尚不是按工序领料点优化的批次预约引擎。生产使用前应确认工厂接受订单齐套 SOP；若采用分批领料、工序级提前投料，需要进一步增加数量、批次、消耗时点和替代料的显式领域模型。

存在没有落实库存/在途供给的外购物料时，CP-SAT 拒绝生成计划。旧引擎的 `materialDelayMap` 基于资源队列推导等待，不能冒充确定到货；本引擎不会把“采购提前期估计”视为已存在的供应。

## 六项目标与质量保护

统一成本沿用既有口径：优先级倒序惩罚、最晚完工 UTC epoch 秒、末工序逾期整分钟、资源加工整分钟负载平方、依赖等待整分钟、实际相邻不同物料切换次数。权重来自策略，同一次求解不改变。

资源 circuit 表示真实邻接，避免把所有不同物料对都计作切换。毫秒时序和成本分钟取整分别处理。乘加使用溢出检查，模型通过 OR-Tools validate 后才求解。专项测试使用 `UPDATE_SCORE_ONLY` 与 Timefold 的六项约束流对照；正式接受结果不依赖影子变量监听器。

审计保存输入哈希、可回放 worker 请求、模型版本、原始求解状态、整数业务成本、目标下界、基线接受标志、基线成本/指标、计算线程、随机种子、各阶段耗时、分支/冲突计数及最终任务。

`FEASIBLE` 仅表示可行；`OPTIMAL` 是当前有限计划窗口、模型和目标口径内的最优结论。目标界不能证明现实生产的全局最优，也不能与另一套目标直接比较。`UNKNOWN` 没有可行基线时不发布。`INFEASIBLE` 不自动放宽冻结或物料约束。

## 配置与构建

需要 JDK 17、Maven、对应平台原生运行环境。

```bash
mvn -f aps/pom.xml clean package
```

主服务配置（默认关闭）：

```yaml
aps:
  cp-sat:
    enabled: true
    worker-jar: /opt/aps/jvs-aps-ortools-worker-1.0.jar
    candidate-tenants: approved-tenant-a,approved-tenant-b
    max-tasks: 300
```

worker jar 必须使用绝对路径，且由部署过程控制。不要允许 API 用户选择任意可执行文件。生产部署将主服务及 worker 放在受限容器/服务账户内，设置操作系统 CPU、内存及 PID 限额；`-Xmx512m` 只限制 Java 堆，不能限制 JNI 原生内存。

启用候选模式前，执行 `aps/sql/20261125_cpsat_time_precision.sql`，将正式、待确认、调整三张任务表的起止时间扩展为 `DATETIME(3)`。CP-SAT可能产生毫秒级边界，原来的秒级字段会改变排程结果。服务端在候选发布前检查六个字段的精度，不满足时拒绝求解；验收逐项比较审计时间和实际入库时间。

策略示例：

```json
{
  "solverEngine": "ORTOOLS_CP_SAT",
  "direction": "FORWARD",
  "materialConstrained": true,
  "solverProfile": "DEFAULT",
  "solveTimeSeconds": 120,
  "scoreCalculationCountLimit": null,
  "maxNoImprovementTime": 0,
  "randomSeed": 17,
  "adaptive": {"enabled": false},
  "cpSat": {
    "executionMode": "SHADOW",
    "horizonDays": 30,
    "numWorkers": 1,
    "useBaselineHint": true
  }
}
```

先运行 SHADOW，完成同输入对照和边界验收后，将授权租户策略改为 CANDIDATE。影子结果只进入审计，页面隐藏确认与预览操作。候选沿用既有确认门禁，源数据变化后必须重新生成。

默认单线程有利于可复现；墙钟终止仍受硬件与进程启动影响，不能承诺逐位重现。每个服务实例最多同时运行两个 worker，合计最多八个配置线程。当前是同步监管的单次子进程协议，没有持久 worker 池或分布式任务队列；服务异常退出时 worker 通过父进程/截止时间守护退出。

总监管窗口为策略秒数加十秒进程退出宽限，包含主服务编译和进程启动；worker 将原生加载及建模时间从内部搜索预算扣除。取消每 100ms 检查一次，终止进程后清理临时文件和令牌；接近截止时间的 I/O 与审计开销仍应监控。macOS 本次原生冷启动约需十余秒，建议从 60–120 秒预算开始校准。

规模门槛：默认 300 个活动任务（worker 绝对上限 500）、150000 个日历分段、100000 个资源排序候选、最大 180 天（包含冻结历史）、32MiB 请求和 16MiB 响应。达到门槛应先分区/缩短窗口，不无限增加线程。

## 验证与复现

```bash
# 复用 aps/scripts/e2e-local.yml 配置，启动独立 aps_e2e MySQL/Redis 和新后端后：
python3 aps/scripts/e2e_cpsat.py --disposable
cd aps-ui
npm test
npm run build
```

脚本只允许操作预置的本机 `aps-ade-e2e-mysql` 容器中的 `aps_e2e`，会清理其 demo 租户排程数据。不得对业务数据库执行。

验收记录及真实页面截图归档在 [CP-SAT 端到端验收](e2e/ortools-cpsat/README.md)。场景覆盖影子不发布、候选与四类预览、数据过期确认拦截、租户隔离、冻结/停机/插单/物料延期、取消、实际预约到料、未落实供应拒绝。单次合成样本用于验证功能和记录差异，扩大使用前应按工厂真实规则、多个规模和随机种子开展对照。

## 本次交付边界

本次完成的是受能力门禁保护的正排引擎及实际业务闭环，不等于原规划文档中所有远期阶段已经交付。逆排、跨午夜未拆分班次、工序级批次预约、共享人力/工装累积资源、运输节拍、分布式 fencing/lease、不可行核心诊断、自动选择局部修复子问题和持久 worker 池，仍须独立建模与验收。当前遇到不支持的已知输入会拒绝；尚未存在于系统领域模型中的资源规则不能被宣称已校验。
