**实测中修复的问题**

- MyBatis 租户过滤与分页拦截顺序导致统计总数包含其他租户。
- 任务与资源双向引用在 DTO 转换时触发循环序列化；改为显式字段映射。
- 异步任务尚未初始化进度时，前端读到 NONE；在受理请求时同步初始化。
- 冻结任务缺少前置任务时没有明确的预检错误；现在在求解前拒绝。
- 无登录会话时可通过身份头或查询参数获取管理员身份；现在默认仅使用会话，旧入口须显式启用。
- 重排重复拆解派生订单，以及冻结任务与新任务引用同一业务补充订单的不同对象；现在仅拆主需求并统一订单引用。
- Java HTTP/2 升级请求导致本地模型服务超时；固定 HTTP/1.1，并支持 JSON_SCHEMA。
- 模型可能混用事件类型与时间字段；应用独立拒绝，不依赖推理服务执行 Schema。
- OptaPlanner 的列表内冻结任务与排除冻结任务的值域不一致，出现正初始化分数；冻结任务改作列表外问题事实，结果门禁严格要求 initScore 为零。
- 直接进入计划页时缺少明确容器高度，正式资源甘特图 canvas 高度为零；补齐页面高度后实测 canvas 高度恢复为 620px，并重新检查截图与前端生产构建。

**复现 MiniCPM + Timefold 真实闭环**

在 `~/.zshrc` 配置相互匹配的 `MINICPM_NEW_BASE_URL`、`MINICPM_NEW_API_KEY`、`MINICPM_NEW_MODEL`。本轮使用 MiniCPM5-2B。启动器每次重新读取该文件，凭据仅进入进程环境，不写 YAML、启动参数或验收报告；不跨配置复用密钥。

```bash
# Java 17 已配置；先停止占用 31010 的本次测试后端。
APS_MINICPM_TLS_PROTOCOLS=TLSv1.2 APS_MINICPM_PREFER_IPV4=true zsh aps/scripts/run-minicpm-e2e.zsh
# 另一个终端，从仓库根目录执行：
source ~/.zshrc
APS_SMALL_MODEL_NAME="$MINICPM_NEW_MODEL" PYTHONDONTWRITEBYTECODE=1 python3 aps/scripts/e2e_minicpm.py
```

测试需要前面的隔离夹具及已确认、包含部分报工任务的基线计划。脚本核对模型输出的事件类型、ID 和所有时间，确认提取阶段业务表校验和不变；只将原始且核对正确的模型结果提交给 Timefold，然后验证冻结、停机、来料边界、模型解释、预览和确认写库。模型或网络失败时直接停止，不使用手写候选替代。TLS 与 IPv4 参数是本机连接兼容设置，HTTPS 证书校验保留。
