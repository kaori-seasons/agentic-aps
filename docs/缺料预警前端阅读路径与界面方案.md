# 缺料预警前端阅读路径与界面方案（计划员视角）

`docs/缺料预警与推送接入方案.md`（设计方案）、`docs/缺料预警实现及验收.md`（后端实现）的续篇。后端链路已上线，本篇回答一个问题：**计划员打开系统之后，缺料从哪里被看见、沿着什么路径读完、在哪里闭环**。范围：`aps-ui` 前端。

版本：2026-11。读者：前端实现者、计划员与计划经理（评审用）、实施培训者。

---

## 0 摘要

结论是一个工作台、五个嵌入点、三期排期：

- **一个工作台**：新增"缺料预警"页（菜单挂在"生产计划"组）。页面按两条预警线分组，齐套线（订单维度）默认展开，水位线（周维度）默认折叠——这是设计方案的硬性要求（方案 7.1：分开字段不够，界面必须默认分组且水位线折叠）。
- **五个嵌入点**：排产进度对话框、订单甘特图、计划确认阻断提示、物料需求甘特图、需求预测页。计划员不需要每天主动打开工作台——他在自己的主场（排产计划页）干活时，缺料信息主动出现在动线上。
- **阅读路径六步**：得知 → 总览 → 分诊 → 深读 → 行动 → 验证闭环。每一步有明确的入口、API、退出条件，见第 2 节。
- 后端接口全部就绪（方案 5.6 全量 + 两个等价入口），**前端不需要后端新增任何接口**；需要新增的只有一个前端时长格式化工具。

## 1 计划员是谁、现在怎么干活

### 1.1 现有页面地图与动线

菜单四组（后端 `ApsAuthService.buildMenuTree()` 下发）：基础数据、生产工艺、生产计划、系统治理。计划员的日常动线集中在：

| 动线 | 页面 | 路由 | 计划员在这里做什么 |
| --- | --- | --- | --- |
| 主场 | 排产计划 | `/productionSchedulingPlan` | 生成排产 → 看进度 → 甘特预览（资源/订单/物料需求三个 tab）→ 提交或放弃 |
| 备料 | 来料计划 | `/materialPlan` | 看在途采购单什么时候到 |
| 订单 | 生产订单 | `/productionOrder` | 看订单交期与排产状态 |
| 补货线 | 需求预测与补货 | `/demandPlanning` | 物控/采购主场，计划员偶尔看"异常与回测" |

### 1.2 现状痛点（后端方案第 1 节的前端投影）

1. 缺料被折算成开工日期往后推，然后在界面上**消失**。计划员在甘特图上只看到"这单排得靠后"，看不到缺什么、缺多少、为什么。
2. **隐形缺料完全无入口**：手上有在途、但到货晚于交期被扣减跳过的那批货，过去任何页面都不体现。
3. CP-SAT 引擎因外购件缺口**拒绝求解**时，进度对话框只有一句"排程失败"，没有任何解释入口。
4. 计划确认被基础数据变化阻断时（`MRP_RELEASE_BLOCKED`），同样只有一句话。

### 1.3 计划员的问题清单 → 字段映射

阅读路径的本质是"让计划员的每个问题在界面上有一个唯一的、直接的位置回答"。逐条映射（全部来自 `GET /shortage/items` 与详情，字段名即接口字段）：

| 计划员的问题 | 回答它的字段 | 所在层 |
| --- | --- | --- |
| 我什么时候缺什么？ | `orderCode`、`materialCode/materialName`、`requiredAt`（交期） | 列表行 |
| 缺多少？ | `gapQuantity`（缺口）、`requiredQuantity`（毛需求） | 列表行 |
| 多急？ | `severity`、`reasonCode`、响应时限（等级映射 30/120/480/1440 分钟） | 列表行 |
| 为什么缺？ | `onHandConsumed`（在库已扣）、`inTransitConsumed`（在途已扣）、`inTransitSkipped`（在途被跳过）、`supplyMode` | 详情抽屉 |
| 那批晚到的货什么时候能用？ | `skippedLines[].availableAt`（到货+缓冲后的可用时刻） | 详情抽屉 |
| 到底有没有货在路上？ | `supplyMode` + `supplyPlan`：`NONE` 显式渲染"无到货计划"，**绝不留空** | 列表行+详情 |
| 这单被推了多久？ | `delayDuration`（ISO-8601，渲染成"5天0时"）、`earliestStart` | 详情抽屉 |
| 影响哪些任务？ | `downstreamTasks[]`（任务、工序、资源、计划起止） | 详情抽屉 |
| 该干什么？ | 命中规则的 `actionHint`（"立即催料或改期，准备分批"等，服务端模板生成） | 详情抽屉 |
| 我处理过没有？别人处理过没有？ | `status`、`resolvedBy`、`observedCount`（"已观测 17 次"） | 列表行+详情 |
| 数据新鲜吗？ | `dataCutoff`（所依据的数据截止时间）、`runId` | 详情抽屉 |
| 凭什么是我这单背缺口？ | `detail.orderSequence`（扣减位次）、`detail.sortRule`（排序规则）、`detail.onHandStart/onHandReservedEarlier`（期初与此前订单已占用） | 详情抽屉 |

## 2 阅读路径总览（信息架构）

### 2.1 六步闭环

```
① 得知                    ② 总览                 ③ 分诊
排产进度对话框 ──┐   ┌─→ 汇总条（分线 chips）─→ 筛选+列表（齐套线展开）
订单甘特角标 ────┼──→│    P1 x │ P2 y │ …       等级排序、交期排序、订单/物料筛选
顶栏徽标(P2) ────┘   │   水位线（默认折叠）
确认阻断提示 ────────┘
        │
        ▼
     ④ 深读                        ⑤ 行动                     ⑥ 验证闭环
     详情抽屉：缺口事实 / 在途明细 /  确认(ack) / 解决(resolve) /  台账 tab：观测次数、
     影响面 / 归属依据 / 处理轨迹      静默(mute，P1 禁用)          推送记录、回执、
                                      ↓                          SUPERSEDED 接续链
                                   去催料/改期（在 APS 之外）→ 下一轮求解自动关闭 → 回到 ①
```

六步的退出条件：①→② 点进工作台；②→③ 点某个等级 chip 或直接扫列表；③→④ 点行；④→⑤ 做出判断；⑤→⑥ 留下处理痕迹；⑥→① 等下一轮求解刷新事实。**闭环的证据是 `jvs_shortage_notify` 的回执，不是人的记忆**——没有回执的预警不算送达（方案 5.5）。

### 2.2 三条设计原则（从方案约束推导，界面不得违背）

1. **两条线不混排**。齐套线（ORDER，"这单能不能干"）与水位线（WEEK，"该不该补货"）对缺料的定义不同。列表默认只展开齐套线，水位线折叠为一条汇总行。混排会让计划员得出"怎么这么多缺料"的错误结论（方案 7.1 原话）。
2. **空值显式**。`supplyMode=NONE` 必须渲染"无到货计划"徽标，不能把 `expectedEta` 留空白——空白会被读成"到货时间待定"，而事实是根本没有在途（方案 3.3）。
3. **事实与判断分离**。欠料清单是事实（缺口数量、扣减过程），等级是规则给的判断。详情抽屉里两者分区呈现，规则可配（计划经理），判断错了改规则而不是改数据。

### 3.3 汇总条

数据源：`GET /shortage/items?...` 响应里的 `summary`（与筛选条件无关，始终是全量分线计数，后端已实现）。点击 chip 即设置对应筛选（等宽数字徽标用 element 的 `el-badge`）。

| 区块 | 字段 | 渲染 |
| --- | --- | --- |
| 齐套线 chip | `summary.ORDER.active / P1 / P2 / P3 / P4 / NO_SEVERITY` | "齐套线 12 · P1 5 · P2 6"，等级色点 |
| 水位线折叠头 | `summary.WEEK.*` | 折叠行标题带计数，默认收起 |
| 数据质量折叠头 | `GET /shortage/alerts?dimension=SYSTEM` 的计数 | "数据质量 2 条待处理"；无 `aps:shortage:handle` 时只读。注意：`summary` 只按欠料条目分线统计，系统级预警没有条目，此组从台账接口取数 |

右上角操作：
- **刷新**：重新拉列表（首版不做自动轮询，见 9.2）。
- **扫描**（`v-permission="'aps:shortage:config'"`）：调 `POST /shortage/scan`，把返回的计数（`alerts.created/repeated`、`dispatch.sent/dead`、`dataQuality` 备注）用 `el-result` 弹层展示——手工扫描本就是验证手段，结果必须可见。

### 3.4 齐套线列表（默认展开组）

列定义（顺序即阅读优先级）：

| 列 | 来源字段 | 渲染规范 |
| --- | --- | --- |
| 等级 | `severity` | 色条+文字：P1 红 `danger`、P2 橙 `warning`、P3 黄 `warning`（浅）、P4 蓝 `info`；`NO_SEVERITY`（字段空）灰字"未定级"，**不是 P4** |
| 订单 | `orderCode` | 链接样式；点击带 `orderCode` 跳生产订单页或就地筛选 |
| 物料 | `materialCode` + `materialName` | 两行：编码加粗、名称灰色小字 |
| 缺口 | `gapQuantity` / `requiredQuantity` | 主行"缺 120 件"（六位小数去尾零），副行灰字"毛需求 300" |
| 需求时刻 | `requiredAt` | `MM-DD HH:mm`；已过交期的行此列红字 |
| 供给状态 | `supplyMode` + `expectedEta` | 徽标四态：`IN_TRANSIT` 绿"在途可用·eta"、`IN_TRANSIT_LATE` 橙"在途晚到·eta"、`PURCHASE_PROPOSAL` 蓝"建议已批·eta"、`NONE` 红"**无到货计划**"（eta 位置留短横，禁止空白） |
| 状态 | `status` | `OPEN` 红"未处理"、`ACKNOWLEDGED` 蓝"已确认"、`RESOLVED` 绿"已解决"（默认过滤器不含 `MUTED`，见 3.8）、`MUTED` 灰"已静默" |
| 观测 | `observedCount` | tooltip："已被 N 轮求解观测到"；N=1 不显示 |
| 操作 | — | `⋮` 下拉：确认 / 解决 / 静默（见 3.6） |

默认排序沿用后端（等级→交期→物料）；默认过滤器 `state in (OPEN, ACKNOWLEDGED)`（后端默认行为）。水位线组列定义同表，但把"订单/需求时刻"换成"地点 `locationCode` / 周 `weekAt`"，"缺口"副行换成"安全水位 `safetyStock` · 场景水位 `scenarioBalance`"，供给状态换成"来源 `reference`（在途行/采购单）+ 原因 `sourceReason`"。

### 3.5 详情抽屉（`el-drawer`，点行打开）

调 `GET /shortage/items/detail?shortageKey=...`。五个分区，自上而下按计划员的追问顺序：

**A. 结论区（判断）**：等级 tag + `reasonCode` 中文名 + 服务端标题 `payload.title`（如"订单 WO-417 缺料 M-10023（高压胶管总成），缺 120 件，交期 11-28 08:00"）+ 建议动作 `actionHint`（高亮框）+ 响应时限（P1"30 分钟内响应"）。

**B. 缺口事实区**：毛需求 `requiredQuantity` → 在库已扣 `onHandConsumed` → 在途已扣 `inTransitConsumed` → 在途被跳过 `inTransitSkipped` → **缺口 `gapQuantity`**，用一个横向瀑布/步骤条呈现，最后一级加粗。旁边给 `dataCutoff`（"依据 11-27 06:00 的数据"）与 `runId` 短码。

**C. 在途明细区**：两张小表，同结构——`skippedLines`（"因晚于交期被跳过"，橙头）与 `availableInTransit`（"参与分配"，绿头）。列：行号 `lineCode`、数量 `quantity`、本次分配 `usedQuantity`、到货 `deliveryTime`、可用 `availableAt`。**C 区是隐形缺料的显影处，必须完整展示，不做分页。**

**D. 影响面区**：`earliestStart`（最早可开工）+ `delayDuration`（渲染"5天0时"，前端加 20 行的 ISO-8601 时长格式化函数，放 `src/util/`）+ `downstreamTasks` 表（任务 `taskCode`、订单、工序 `processCode`、资源 `resourceName`、计划起止）。行尾"在甘特图查看"链接 → 跳订单甘特图对应订单。

**E. 归属与轨迹区**（默认折叠）：归属依据 `detail`——扣减位次（"本单第 4 个扣减，排序规则 priority DESC, deliveryTime ASC"）、期初 `onHandStart`、此前订单已占 `onHandReservedEarlier`、出现次数 `occurrences`、提前期/缓冲期；处理轨迹——`status` 流转、`resolvedBy/resolvedAt/resolutionNote`、`firstDetectedAt→detectedAt`（"连续缺料 3 天"）。此区回答"凭什么是我背缺口"（方案 7.3 的留档在前端的呈现）。

### 3.6 行动区（处理）

统一走 `POST /shortage/items/handle`，body `{shortageKey, action, note}`；也支持路径式 `/items/{shortageKey}/ack|resolve|mute`。规则：

| 动作 | 权限 | 交互 | 后端语义 |
| --- | --- | --- | --- |
| 确认 ack | `aps:shortage:handle` | 无弹窗，行内确认；toast"已确认，处理中" | 条目与其全部预警 → ACKNOWLEDGED |
| 解决 resolve | `aps:shortage:handle` | 小弹窗必填处理说明（≤500 字）+ 常用理由快捷项（"已催料到货/已改期/已分批/订单取消"） | → RESOLVED；**未投出的推送自动取消** |
| 静默 mute | `aps:shortage:handle` | 按钮在 `severity==='P1'` 时**禁用**并附 tooltip"P1 已影响上线，不允许静默"（后端也会 409，前端先拦一层）；其余等级弹窗必填理由 | → MUTED；默认列表不再显示 |

处理完成后**就地刷新该行**（不整页重载）。后端 409/422 的 `msg`（"P1 预警不允许静默…"、"静默必须填写理由"）直接 toast，两端口径一致。

### 3.7 状态机与行的视觉

```
OPEN ──ack──→ ACKNOWLEDGED ──resolve──→ RESOLVED
  │                │
  └────mute───────→ MUTED（P1 禁止；新轮求解若未再观测，保持 MUTED 不被系统改写）
  任何未终结状态：等级升级（P3→P2）时旧预警置 SUPERSEDED，新预警接续
```

- `OPEN` 行：左侧等级色条 4px；`ACKNOWLEDGED` 行：色条变蓝、文字常规；`RESOLVED`（仅 includeClosed 视图可见）整行 50% 灰；`MUTED` 行灰且带"已静默"角标，提供"取消静默"入口（再次 handle 成 ack 即可恢复）。

### 3.8 视图切换与筛选细节

- 状态过滤器选项：未处理（默认）/ 已确认 / 已静默 / 已解决 / 全部。选"已解决/全部"时请求带 `includeClosed=true`。
- 订单号、物料编码输入框：精确匹配（后端 `orderCode`/`materialCode` 为等值查询），placeholder 注明"精确匹配"。
- 分页：50/页（接口上限 500），沿用 demandPlanning 页"上一页/下一页"按钮样式。
- `shortageKey` 含冒号等保留字符：详情与处理一律用查询参数入口（`/items/detail?shortageKey=`、`/items/handle`），**不要**把 key 拼进路径。

## 4 P1：预警台账 tab（同一工作台的第二个 tab）

数据源 `GET /shortage/alerts?dimension=&severity=&status=&ruleCode=&since=`。定位：不是给计划员日常看的，是**审计与闭环验证**（第 ⑥ 步）与"为什么我没收到推送"的排查入口。

| 列 | 字段 | 说明 |
| --- | --- | --- |
| 等级/规则 | `severity` + `ruleCode`（中文名映射表前端维护） | 排序列 |
| 标题 | `title` | 服务端模板生成，前端原样渲染，**不重新拼接**（各渠道文案一致的前提） |
| 状态 | `status` | 五态含 `SUPERSEDED`（"已被更高等级接续"，tooltip 展示链） |
| 观测 | `observedCount` + `lastObservedAt` | "观测 17 次，最近 11-27 10:00"——避免误以为只发生一次（方案 5.4） |
| 推送 | `pushedCount` + `lastPushedAt` | "已推 1 次"；0 次且非 LEDGER 时黄标"未送达" |
| 处理 | `acknowledgedBy/At`、`resolutionNote` | |
| 操作 | — | 查看 payload（`el-drawer` 内 JSON 树，只读）；跳转欠料条目（`shortageKey` 回工作台列表） |

单条预警的推送记录：点行 → `GET /shortage/notifies?alertId=...`，展示每渠道每次投递（状态 SENT/DEAD/SKIPPED、尝试次数、HTTP 状态、`lastError`、回执 `receiptState/By/At`）。`NOTIFY_DELIVERY_FAILED` 这类系统级预警在这里只进台账——它是"推送不出去"的元预警，界面上不再往失效渠道外推。

预警级回执 `POST /shortage/alerts/{alertId}/ack|resolve|mute`（权限 `aps:shortage:dispatch`）保留给渠道回调与外部系统，**界面上不提供按钮**，避免与条目级处理形成两个入口。

## 5 P2：规则配置页（计划经理）

数据源 `GET /shortage/rules`（默认值+覆盖值同回）与 `PUT /shortage/rules/{ruleCode}`。

- 表格一行一规则：规则码/中文名/维度、默认值列（灰字只读：`defaultSeverity/defaultThresholdValue+defaultThresholdUnit/defaultCooldownMinutes/defaultReceivers/defaultChannels/defaultActionHint`）、生效值列（可编辑）、"已覆盖"角标（`overridden`）。
- 编辑交互：行内"覆盖"按钮 → 弹窗只含被改字段（下拉：等级、启用、阈值+单位 DAYS/HOURS/MINUTES、冷却分钟、接收角色多选、通道多选、建议动作）；**只提交改动字段**（后端按字段 coalesce）。
- "恢复默认"按钮：**当前后端做不到**——覆盖接口的空值语义是"不修改"（按字段 coalesce），一旦覆盖无法清空回默认。需后端补一个删除覆盖行的入口（如 `DELETE /shortage/rules/{ruleCode}` 或 `PUT` 带 `reset=true`），列为 P2 的后端配套小项；在补齐之前界面隐藏该按钮，避免假恢复。
- 硬约束的界面表达：站内台账通道不可取消（后端总是并回 LEDGER）——通道多选里 LEDGER 勾选禁用；`DATA_STALE`/`SYNC_DEAD_LETTER` 行标注"待同步通道启用"且禁用编辑。
- 阈值标定提示（方案 4.5）：页头常驻 `el-alert`："默认阈值来自通用生产节奏，非本厂事实数据，上线前须按实际节奏标定。"
- 权限 `aps:shortage:config`（计划经理、运维）。

## 7 状态、文案与口径规范

### 7.1 等级与状态色（element-plus 映射）

| 语义 | tag type | 说明 |
| --- | --- | --- |
| P1 红 | `danger` | 已影响上线/无法按期，30 分钟内响应 |
| P2 橙 | `warning` | 3 天内会缺/承诺失效，2 小时内响应 |
| P3 黄 | `warning`（plain） | 14 天内/低于安全水位，当班内响应 |
| P4 蓝 | `info` | 数据质量提示 |
| 未定级 | 文字灰 | 未命中任何规则，**不得**渲染成 P4 |

### 7.2 数量与时间

- 数量：接口给六位小数字符串，界面去尾零显示（"120"而非"120.000000"）；详情抽屉的瀑布保留两位小数。
- 时间：`YYYY-MM-DD HH:mm`；`expectedEta` 若在 48 小时内，加"3 天后/8 小时后"相对时间后缀。
- `delayDuration`（ISO-8601 如 `PT120H`）：新增前端工具 `formatIsoDuration` → "5天0时"；解析失败兜底显示原串，不隐藏。

### 7.3 文案银行（copy bank）

| 场景 | 文案 |
| --- | --- |
| 列表空态（齐套线） | "当前没有未处理的齐套缺料。生成排产后此处自动汇总。" |
| 列表空态（水位线） | "当前没有未处理的水位预警。" |
| 搜索无结果 | "没有匹配的缺料记录，试试清空筛选。" |

| 解决弹窗 placeholder | "处理说明（必填）：如已向 SUP-0087 催料，预计 11-30 到货" |

### 7.4 两条线冲突的话术（方案 7.4 要求的培训口径，落进界面）

详情抽屉 E 区固定一段灰字帮助："齐套线回答**这单能不能干**（按订单需求扣在库与可用在途），水位线回答**该不该补货**（按周对比安全库存）。同一物料可以'本单齐套'同时'低于安全水位'——这不是数据错误，是两个问题。前者找采购催料，后者走补货审批。" 首次进入工作台时以 `el-alert`（可关闭，localStorage 记忆）完整展示一次。

## 9 性能、刷新与数据量

### 9.1 数据量与接口习惯

- 列表接口不带 payload 大字段（后端已裁剪），单页 50 条；`summary` 由后端聚合返回，前端**不要**自行累计全量。
- 筛选条件下推服务端（dimension/severity/status/orderCode/materialCode），前端不做本地过滤。
- 台账列表当前即随行返回解析后的 `payload`，前端直接可用；若后续量大出现性能问题，再优化为列表瘦身 + `GET /shortage/alerts/{alertId}` 按需拉取（后端两形态都已支持）。

### 9.2 刷新策略

- 首版：**手动刷新 + 关键事件刷新**（E1 求解完成后、E4 确认失败后、处理动作完成后）。不做轮询、不做 WebSocket——后台复评每 5 分钟一轮，轮询界面只会放大"观测次数"的迷惑。
- 竞态：`keepAlive: false` + 进入页面时带时间戳参数请求；处理动作完成后只刷新受影响行（按 `shortageKey` 重拉详情+列表当前页）。
